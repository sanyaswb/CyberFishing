# Критичний огляд коду перед push

Власник, 2026-11-16: «пропиши в документі як ти діяв і як повинна діяти наступна сесія для перевірки будучи таким
критиком, для виявлення багів і деоптимізацій, детальні ревью і cleanup, це треба додати до правил перед пуш».

Огляд — обов'язковий крок перед **кожним push** (AGENTS.md «Pushes and Pages releases»). Агент читає зміни як критик:
шукає баги, конфлікти між модулями, деоптимізацію, дублювання (DRY), порушення архітектури (шари, ООП, одна
відповідальність) і слабкі перевірки; виправляє знайдене окремими задачами з перевіркою, що падає на старому коді. UI
агент не тестує: вигляд перевіряє власник.

## 1. Межі огляду

- Обов'язково: усе, що піде в push — `git log --oneline origin/develop..HEAD`, `git diff --stat origin/develop..HEAD`.
  Згрупувати зміни за областями (погода, сцена, інвентар, DevTools, перевірки…).
- Читати **модулі повністю**, а не лише diff: баг часто в старому коді поруч із новим (так знайдено TK-358.1).
- Коли власник просить «пройдись по всьому X» — вся область X, не лише свіжі коміти.
- Інші сесії могли комітити в ту саму гілку (`git log` з авторами): їхні коміти теж в огляді.

## 2. Що прочитати перед оглядом

- `docs/incidents.md` → «Rules at a glance» (R1…): кожне правило — відома пастка.
- `docs/rendering.md` (для сцени, HUD, кадрів), `DEVELOPMENT_RULES.md` (шари, ін'єкція, гарячі цикли),
  `docs/architecture.md`, `DESIGN_RULES.md` / `docs/styles.md` (для UI).
- Для кожної бібліотеки, на поведінку якої спирається код (Pixi, Spine) — її код у `vendor/` (правило «Library contracts»):
  не документацію з пам'яті, а саме те, що лежить у репозиторії.

## 3. Перелік перевірок (як діяти)

### 3.1 Дублювання (DRY) і перевикористання

1. Спершу шукати, **що вже є**: `src/engine/math/` (`number_normalization.js`: `clampUnit`, `finiteOr`, `pairValue`,
   `pairBetween`…; `rectangle_bounds.js`: `regionsBounds`…), спільні частини сцени (`screen_zone_set.js`,
   `zone_rect_mask.js`, `background_placement.js`, `scene_color.js`), presentation-каталоги (`STATUS_LABELS`…).
2. Шукати копії приватних хелперів і методів у сусідніх модулях:
   ```bash
   grep -rln "const clamp01 =\|const number = (value, fallback)\|const finite =\|const pairAt =" src
   grep -rn "  #prepareZones(\|  #updateMask(\|  #placeView(\|static #color(\|maskRects" src
   ```
   і загалом: однакові назви приватних методів у кількох файлах (`grep -rho "  #[a-zA-Z]*(" src/<область> | sort |
   uniq -c | sort -rn`), однакові формули, однакове форматування тексту.
3. Копію замінити спільним класом (одна відповідальність, конструкторна ін'єкція, без `Manager/Utils/Helper`) або
   наявним хелпером. Перевикористовувати, а не дописувати ще одну версію. Порядок викликів випадкових чисел і
   поведінку зберігати; якщо змінюється — сказати власнику.
4. Дубль **представлення** в UI (той самий стан у двох місцях DevTools / HUD) — теж дублювання (DESIGN_RULES
   «Intuitive interaction»): лишити одне місце, прибрати порт, який став непотрібним (довести, що споживачів немає).

### 3.2 Стан і життєвий цикл (найчастіші справжні баги)

- **Поле, яке встановлюється, але ніколи не скидається:** ручні утримання, «override», кеші «наступного разу», лічильники.
  Приклад: `WeatherEventProcess.#smoothSecOverride` жив після зняття утримання (TK-358.1).
- **`dispose()`**: чи все звільняється (таймери, підписки, текстури), чи композиція реєструє об'єкт через `own()`, чи
  `dispose` скидає **разом із таймером і поля, що описують таймер** (TK-358: `#timerAtMs`).
- **Стан «зроблено», записаний до перевірки, що справді вдалося:** виклик міг не спрацювати (немає опису, немає даних) —
  тоді не запам'ятовувати успіх (TK-358: `RadiationStatusSource`).
- **Лічильники подій і базові значення:** перший кадр бере лічильник як є (не стріляє подією), скидання кадру не
  повинно давати хибну «зміну» (болід `bolideSerial`).
- **Пари «увімкнути / вимкнути»**: чи симетричні; чи вимкнення в будь-якому порядку не залишає чужого стану (R22).
- **Межі часу:** вікна через північ, стрибки годинника вперед, великий `dt` після прихованої вкладки.

### 3.3 Контракти бібліотек

- Кожне використання Pixi / Spine звірити з `vendor/`: маски (одна маска — один контейнер; знята маска знову
  малюється — TK-356.1), `ParticleContainer` (одна текстура на всі частинки; динамічні властивості), кеші меж спрайтів.
- Тестовий двійник бібліотеки моделює той самий контракт (R1); якщо ні — доповнити двійник (так `fakePixi` отримав
  контракт маски) і перевірити, що всі наявні сценарії з ним проходять.

### 3.4 Продуктивність (деоптимізація)

- Гарячі цикли (кадр): жодних алокацій (`{}` / масивів / замикань / `for…of` по Map у кожному кадрі), повторно
  використані записи, робота лише при зміні, кадр сцени лише коли щось рухається.
- Невидиме не рахується: частинки народжуються лише у видимій частині, густота — частка видимого від усієї локації
  (TK-355), фільтри й маски обрізані екраном.
- Рахувати шари на весь екран, трафаретні маски, виклики малювання, нові текстури; нове — записати в `rendering.md` і
  попросити в власника вимір «ПРОДУКТИВНІСТЬ» на телефоні.
- Замір навантаження без UI: Node-скрипт у `utils/tmp/<назва>/`, справжні рендерери на двійнику Pixi з
  `scene-layer-check.js` (витягнути `fakePixi` / `fakeDom` у тимчасовий модуль), найгірший випадок налаштувань,
  `performance.now()` на кадр, середнє й p95 після розігріву; результат — у задачу, тимчасові файли видалити.

### 3.5 Перевірки (tests)

- Кожна перевірка нового коду **падає на старому**: старий файл на місце, перевірка, відновлення байт у байт (`cmp`).
  Якщо перевірка падає структурно (TypeError), а не на твердженні про суть — сказати про це.
- Шукати перевірки, що проходять випадково: порівняння відфільтрованого списку з вихідним за позицією (R25), залежність
  від випадкового місця появи частинки, межі «рівно в кадр».
- Двійники тримають контракт (R1, R24); тести не пишуть у джерела проєкту.

### 3.6 Архітектура

- Шари: engine ← game (domain, application) ← platform / presentation ← bootstrap; production не залежить від DEV.
  `npm run check` містить `architecture`, але й читати: чи нова логіка в правильному шарі (правила — domain, стан —
  application, малювання — platform/presentation).
- Один модуль — одна відповідальність; текст для гравця — у presentation-каталогах; значення гри — у конфігу з
  підписами DevTools і перевіркою схеми.
- Мертвий код після змін (методи, порти, конфіг без читача) — прибрати, довівши, що споживачів немає.

### 3.7 Документи

- `rendering.md`, `incidents.md` (значущий дефект — запис і правило), `architecture.md`, специфікація («Реалізація»),
  `tasks.md`, бекрог геймплею: відповідають коду після змін.

## 4. Як виправляти знайдене

1. Записати знахідку в `tasks.md`: нова `TK-NNN` або підпункт `TK-NNN.N`, якщо це виправлення наявної задачі
   (що знайдено з `файл:рядок`, причина, що змінюється, перевірка).
2. Перевірка, що падає на старому коді; виправлення; фокусні перевірки; один Full (`npm run check`, game-cycle без змін
   або погоджений перебазис).
3. Рефакторинг без зміни поведінки — окремим комітом від виправлень, якщо їх можна розділити; доказ незмінності —
   наявні перевірки проходять без правок очікувань.
4. Patch-версія, CHANGELOG, локальний коміт з фактичним повідомленням (що знайдено, причина, як перевірено).
5. Наприкінці — звіт власнику: знахідки за важливістю, що виправлено, що ні й чому, що подивитися візуально.
