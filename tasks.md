Візуальне приймання власником очікується.

- **v0.45.14 — адаптивна нижня панель:** місце під відкритий селектор зарезервоване постійно; кнопки зліва не зсуваються при його відкритті. За браком ширини ряд переноситься вище; плашка версії прихована до 820 логічних px ширини панелі. Поплавок відкриває горизонтальний повзунок у потоці зі спільними відступами. Прибрано дубльовані JS-розрахунки, зміни плашки двома компонентами та глобальні layout-події. Візуальне приймання власником очікується.

- **v0.45.9 — уточнення після скасування:** у відкритої кнопки велика дуга зверху зліва та заокруглення лише нижнього правого кута; верхній правий і нижній лівий — прямі. Візуальне приймання очікується.

- **v0.45.6 — анімація форми селектора:** закритий селектор має спільну квадратну форму кнопок із заокругленими кутами. Закриття повертає квадрат; зменшений рух перемикає форму одразу. Візуальне приймання власником очікується.

- **v0.45.5 — розташування поплавка:** на ПК поплавок стоїть лівіше всіх кнопок, перед прикормкою. Відкритий повзунок не розширює ряд і не посуває прикормку. Мобільне розташування над підсакою та спільні відступи збережено; візуальне приймання власником очікується.

## Межі й робочі припущення

1. **TK-001, уточнення власника:** нижня шторка замінює тимчасові повідомлення **лише до 820 логічних px UI-поверхні включно**, незалежно від орієнтації. Постійні пояснення, валідація, підтвердження й hover-підказки зберігають свої компоненти. «10%» — частка початкової видимої висоти шторки, а не екрана.
2. **TK-002, уточнення власника:** **80 px** — максимальне додаткове горизонтальне випередження, дозволене лише на відповідному краї локації; до досягнення краю воно нульове. 3. **TK-004:** під верхнім блоком кнопок мається на увазі sticky-панель дій редактора предмета `.inventory-assembly-editor__actions`. У початковому тексті інший екран не зазначений.
4. **TK-005:** через відсутність обмеження «лише DEV» вимога поширюється на годинник звичайної гри та його DEV-варіант. House використовує той самий календарний годинник і має підтримувати цю ж дію. Стрибок змінює ігровий час, а не лише картинку фону.
5. **TK-006:** початковий текст трактується як бажана поведінка: вудка лише з котушкою та ліскою рухається без додаткового уповільнення після натягування ліски. Це окремий виняток для порожнього оснащення, а не перебалансування всіх снастей.
6. **TK-007, уточнення власника:** жести потрібні і для вкладок редактора, і для переходів між «Екіпіровкою», «Рюкзаком» та «Садком» у широкій розкладці. Широкий інвентар зберігає свої колонки; свайп перемикає розділ без прихованих проміжних мобільних сторінок.

Ці припущення — конкретизація нечіткого початкового тексту, а не факти про вже погоджений дизайн. Якщо власник уточнить інше значення, спочатку скоригувати відповідне ТЗ.

## TK-001. Тимчасові повідомлення як нижня шторка

**Мета, уточнення TK-001.1:** на телефонах до **820 логічних px UI-поверхні включно** повідомлення виїжджає знизу з ручкою, без нижньої рамки та будь-якого верхнього відступу. На ширших екранах лишається попереднє повідомлення згори з повною рамкою та звичайним закриттям.

**Зараз у коді:**

- [UiHintRenderer](src/game/presentation/ui/ui_hint_renderer.js) створює спільний `ui-hint` із текстом, тоном та кнопкою закриття; сам renderer не володіє автотаймером.
- [InventoryUI](src/game/presentation/inventory/inventory_ui.js), метод `showWarning()`, показує попередження на 5000 ms у `.inventory-modal__hints` над header. House також використовує спільний hint renderer.
- [SheetDismissController](src/platform/browser/dom/sheet_dismiss_controller.js) та [UiSheetHandleRenderer](src/game/presentation/ui/ui_sheet_handle_renderer.js) вже забезпечують жест/доступну ручку. Поточний поріг dismiss задається відстанню в px, а не часткою висоти.
- Уточнення власника зберігає top-flow контракт spec 086 на ширинах >820 px. Нижня шторка стосується тільки телефонної області; поточні DESIGN_RULES/styles синхронізовані з цим обмеженням. Історичний spec не переписувати як нове джерело істини.

**Вимоги:**

Нижче вимоги шторки застосовуються **лише до <=820 px**. Вище межі inventory warning залишається в першому рядку перед header, House notice — у верхній hint-region активної панелі або під header (його показати, якщо панелі немає). Зберегти повну PC-рамку, X і inline-тривалості 5000ms / 4000ms; без ручки, drag і анімації закриття вниз. Ширину читати з інжектованого `UiSurfaceAdapter`, без device/UA-евристик.

1. Одна активна тимчасова шторка на видимому екрані/модальному контейнері. Нове повідомлення замінює попереднє та перезапускає таймер; чергу повідомлень у межах цієї задачі не вводити.
2. Показувати її внизу активної UI-поверхні з урахуванням safe area та split-layout інвентаря. При появі не зсувати header і контент зверху. Не створювати другий modal/focus trap; події всередині шторки не повинні керувати грою під нею.
3. Використати спільні surface/radius/motion-токени. Верхні кути заокруглені, ручка видима, **`border-bottom: 0` лише у шторки**. Зберегти тони info/warning/error, доступне оголошення та клавіатурний спосіб закриття; ручка-кнопка може виконувати роль закриття.
4. Автоматичне закриття — через **5000 ms** після останнього показу. Під час активного drag таймер призупинений; якщо жест не закрив шторку, відлік починається знову. Значення передати конфігурацією, scheduler — залежністю.
5. На початку жесту один раз запам'ятати видиму висоту `H` у логічних координатах. Після розпізнавання вертикального руху шторка слідує вниз за pointer; на release при `dy >= 0.1 × H` завершує закриття під нижню межу екрана. При меншому зміщенні повертається у відкрите положення. Горизонтальний рух сам по собі не закриває.
6. Drag починається з ручки, фону або тексту; використовує один active pointer. Клік по закриттю не породжує команд гри, завершений drag не породжує випадковий клік. `pointercancel` скасовує drag і відновлює відкритий стан, якщо екран ще існує.
7. Довгий текст обмежити за висотою (початкове значення — 50% доступної висоти поверхні) і дозволити читати прокруткою. У текстовому scroller свайп вниз починає dismiss лише з `scrollTop === 0`; інакше жест прокручує текст. Ручка залишається доступною.
8. Нове повідомлення під час закриття починає новий повний показ; старий timer/animation callback не може приховати його. Закриття екрана прибирає шторку та всі її ресурси.
9. Під час перетину 820↔821 скасувати поточний drag/capture й старе закриття, змінити режим і перенести той самий House node без втрати повідомлення; таймер починається для нового режиму. Empty top-region не резервує місця на телефоні: padding/margin селектори не повинні реагувати на абсолютну шторку. Підписки на UI-surface звільняються при dispose.

**Місця змін:** `ui_hint_renderer.js`, власники повідомлень `inventory_ui.js` і House, спільні `styles/modal-controls.css`, локальні місця розміщення в `styles/inventory/modal.css` / House, `inventory_ui_bootstrap.js`, `house_view_composition.js`. Повторно використати чинні sheet-примітиви, якщо вони забезпечують потрібний контракт; не змінювати непов'язані House-жести побічно.

**Критерії приймання:**

- [ ] До 820 px інвентарне попередження з'являється знизу, зникає через 5 s, не має нижньої рамки й не змінює верхній відступ або положення header/контенту.
- [ ] На 821 px і ширше inventory/House повертаються у свої колишні верхні області з повною рамкою; drag не закриває повідомлення, inline-таймери збережені. Resize під час drag/closing не залишає stale exit, дубльованих вузлів або listeners.
- [ ] Для `H = 200` release на 19 px повертає шторку, на 20 px закриває; перевірити також масштаб нижче 320 px.
- [ ] Свайп за ручку, фон і короткий текст працює однаково; довгий текст читається без випадкового закриття під час його прокручування.
- [ ] Заміна повідомлення, повторне відкриття екрана, reduced motion, Escape/кнопка закриття та скасування pointer не залишають завислого стану або timer.
- [ ] У каталозі показано той самий production-компонент у короткому, довгому та warning/error станах.

**Перевірки:** розширити `utils/ui-components-check.js`, `utils/inventory-ui-check.js`, `utils/house-check.js`, `utils/platform-runtime-check.js`, `utils/ui-catalog-check.js`; пороги й timers перевіряти керованим часом. ## TK-002. Плавне горизонтальне випередження прицілу

**Мета, уточнення TK-002.1 / TK-002.2:** поки камера має запас горизонтального руху, приціл збігається з пальцем. Лише після досягнення відповідного краю локації застосовується центрована крива до **80 px**: від'ємне випередження на лівій межі, додатне — на правій. Посередині viewport лінія завжди під пальцем, незалежно від початкового дотику.

**Власник у коді:** [CastPowerAim](src/game/application/casting/cast_power_aim.js) обчислює `screenX` у `update()` та на release. Від цієї координати залежать visual state, preview точності, edge-scroll та реальна ціль. Клас спільний для першого закидання, повторного прицілювання в [WaitingState](src/game/application/state/waiting_state.js) і ручної прикормки в [ChumController](src/game/application/chum/chum_controller.js). До TK-002.1 зсув рахувався від `pointerStart.x`; чинний контракт нижче замінює його на середину поточного viewport.

**Вимоги:**

1. На pointerdown, наступних оновленнях і release перевіряти фактичний край камери для боку `pointerX - viewportWidth / 2`. Поки там лишається можливість pan, `aimX = clamp(pointerX, 0, viewportWidth)`. Правий край не дозволяє ліве випередження й навпаки. За відсутності даних про край не вмикати випередження. Вертикальний рух сам по собі не змінює його.
2. Якщо край досягнуто, застосувати криву: `dx = pointerX - viewportWidth / 2`, `q = clamp(abs(dx) / rampDistancePx, 0, 1)`, `lead = sign(dx) × maxLeadPx × (3q² - 2q³)`, `aimX = clamp(pointerX + lead, 0, viewportWidth)`. Центр завжди дає нульове випередження. Ширина — чинний ігровий canvas у його локальних координатах; у split-layout це ігрова смуга, а не все вікно.
3. Налаштування: `maxLeadPx = 80`, `rampDistancePx = 100`; зберігати в `casting.pointerAim` runtime-config і передавати через чинну залежність. При `maxLeadPx = 0` приціл слідує безпосередньо за pointer. Некоректні значення нормалізувати при зміні конфігурації, а не створювати нові об'єкти щокадру.
4. Крива симетрична відносно середини viewport, без стрибка при поверненні через неї. Знак випередження залежить від сторони екрана, а не напрямку руху: під час повернення справа зсув плавно зменшується до нуля в центрі. Resize використовує нову середину; не утримувати старий горизонтальний anchor.
5. Для visual state, preview, edge-scroll і release використовувати спільний розрахунок `aimX`. Після кроку pan повторити його за фактичним clamped-положенням камери, щоб досягнення/відхід від краю враховувалися в тому самому кадрі. Не зміщувати лише намальовану лінію зі старою ціллю закидання.
6. Нову поведінку застосувати до pointer-прицілювання в усіх споживачах CastPowerAim, включно з прикормкою; mouse-drag працює за тією самою кривою. Keyboard aim залишити з чинною швидкістю, без додаткового випередження.
7. Зберегти вертикальну формулу сили, deadzone, точність/розкид, затримку польоту, перевірку води, скасування нульової сили та перехід до звичайного pan без готового спорядження. Reset і новий жест очищають попереднє випередження.
8. Випередження — функція поточної відстані від центру, а не історії жесту чи частоти pointermove. Рендер і 2D fallback читають чинну модель прицілу; не вводити паралельний стан прицілу в scene renderer.
9. `ViewportProjector` — єдиний власник camera X / horizontal scroll limits. Його read-only directional query визначає дозвіл випередження; не дублювати camera flags у CastPowerAim і не виводити їх із castable bounds. Якщо вся локація вміщується горизонтально, досягнуті обидві межі й крива доступна на обох половинах. Resize використовує актуальні межі й ширину.

**Критерії приймання:**

- [ ] У viewport шириною 400 з вільною камерою `x=150/250` дають ті самі `aimX=150/250`. На лівій межі `150→110`, але `250→250`; на правій — `250→290`, але `150→150`. На обох межах повернення до `200` дає `200`.
- [ ] На відповідній межі, без screen clamp, на відстані 100 px від центру випередження становить рівно 80 px; далі не збільшується. Якщо viewport показує всю локацію, обидві половини використовують центровану криву.
- [ ] Після старту з будь-якого боку й повернення до середини випередження нульове. Відхід камери від межі вимикає його відразу, досягнення межі вмикає в тому самому update. Resize / split-layout не зберігає застарілих меж.
- [ ] Відпускання без останнього pointermove використовує актуальну координату; відображений preview і ціль release узгоджені за фіксованого RNG.
- [ ] Перший cast, long-press recast і прикормка мають однаковий pointer-контракт; keyboard та вертикальна сила працюють як раніше.

**Перевірки:** `utils/task-interactions-check.js` — вільна/крайова реальна камера, дозвіл лише відповідного боку, досягнення/відхід у тому самому кадрі, різні стартові X, центр, 80px cap, clamp, release/preview/target, resize, live/default config і keyboard; `viewport`, `water-metric`, `recast-aim`, `platform-runtime`, game-cycle. Власник: `index.html` / `dev.html`, pan до обох меж і повернення в центр у portrait/landscape, touch/mouse та split-layout.

## TK-005. Перемикання пори доби подвійним натисканням годинника

**Мета:** подвійний tap/click по годиннику переводить світ у наступний стан циклу **день → вечір → ніч → день**.

**Зараз у коді:**

- [TimeDisplay](src/platform/browser/ui/time_display.js) у production пасивний; інтерактивний варіант має один `click` callback.
- [DevTimeControl](src/dev/time/dev_time_control.js) за ввімкненого `debug.timeAccelerationEnabled` одиночним click циклічно змінює прискорення ×1…×5. Звичайний `dblclick` без узгодження спочатку виконав би два одиночні click.
- [GameTimeClock](src/game/domain/time/game_time_clock.js) — власник календарного часу, anchor та rate; API прямого встановлення години ще немає. [GameTimeLocalStore](src/platform/browser/storage/game_time_local_store.js) зберігає v1 `{ anchorHours, anchorMs, timeScale }`.
- [backgroundTimeBlend](src/game/domain/time/background_time_blend.js), emoji годинника та `spawn.timePhases` мають різні пороги. Зокрема фонове «ніч» починається о 21:00, фаза спавну — о 23:00. Не прирівнювати ці системи й не міняти їхні пороги побічно.
- Пасивний production-годинник закріплено в docs/styles та spec 058. **Ця задача є явною зміною контракту**, а не дозволом імпортувати DEV-керування у production.

**Вимоги:**

1. Задати конфігурацією три цільові години: **день 12:00, вечір 19:00, ніч 00:00**. За чинними формулами це чисті фонові стани; 00:00 також відповідає нічній фазі спавну та emoji. «Ранок» не додається до циклу.
2. Для вибору наступного стану класифікувати поточну годину за чинною фоновою композицією: при `night > 0` — ніч, інакше при `evening > 0` — вечір, інакше день. Отже початкові 12:00 дають 19:00; довільна година/світанок мають визначений результат. Пороги фонового blend не копіювати у browser adapter.
3. Два завершені натискання на годиннику з інтервалом **до 300 ms включно** утворюють одну команду; рух понад **8 фізичних CSS px** або `pointercancel` скасовує tap. Обробити mouse/touch без дубля з compatibility click. Параметри розпізнавання передати конфігурацією.
4. У production одиночний tap не змінює часу. У DEV подвійний tap змінює фазу **без двох кроків прискорення**; одиночна дія прискорення виконується після вікна розпізнавання й лише коли ввімкнена. Фаза доступна незалежно від прапорця DEV-прискорення; її зміна зберігає поточні `timeScale` і multiplier.
5. Доповнити GameTimeClock явною операцією зміни години: перевірити скінченне значення в `[0, 24)`, встановити новий anchor на інжектованому `now`, зберегти через чинний save-port. Domain не працює з DOM/localStorage напряму.
6. Годинник, EnvironmentSystem, фон локації й House читають той самий календарний час. Оновити їх на найближчому циклі без перезапуску сцени чи програвання всіх пропущених годин. Наступна природна зміна години продовжується від нового anchor.

## TK-006. Рух вудки без кінцевого оснащення

**Мета:** після закидання вудка з котушкою й ліскою, але без кінцевого оснащення, не переходить на повільний режим лише через геометричне натягування ліски.

**Зараз у коді:** [CastRodControl](src/game/application/fishing/cast_rod_control.js) володіє позицією вудки між закиданням і підсіканням/витягуванням. `#resolveMovementStep()` ділить час кадру на вільний хід і натяг; [CAST_ROD_CONTROL_CONFIG](src/game/config/raw/physics/cast_rod_control_config.js) задає ×3 для `stationaryFloat` та ×1 для `movingFloat` при базових 100 px/s. `update()` не отримує оснащення, тому цей розрахунок сам не відрізняє порожній кінець ліски. [WaitingState](src/game/application/state/waiting_state.js) вже читає `getEquipped()` і викликає цей controller. Готовність до cast у ScoutingState перевіряє rod/reel/line, тож не слід вводити нову вимогу обов'язкової снасті.

**Вимоги:**

1. Класифікувати «порожнє оснащення» за авторитетним equipment/assembly read model: є вудилище, справна потрібна котушка та ліска, немає кінцевої снасті/поплавка або їхніх прикріплених компонентів у воді. Сам факт наявності предмета в рюкзаку нічого не змінює.
2. Для цього випадку залишати швидкість вільного руху і після вичерпання slack: за початкової конфігурації **300 логічних px/s** за повного input, як і до натягу. Не додавати нову модель гідродинаміки чи малий коефіцієнт опору без окремої балансної задачі.
3. Порожній кінець ліски може й далі мати технічну water-entity. Наявність `floatEntity` не є достатньою ознакою справжнього поплавка/навантаження. Передати controller мінімальну ознаку/профіль навантаження з Application; не давати renderer право вирішувати швидкість.
4. Геометрію ліски, обмеження довжини, проєкцію кінця у воду та чинний `lineTensionActive` зберегти. Відсутність уповільнення не означає нескінченної ліски або вимкнення всіх візуальних ознак її натягу.
5. Для будь-якого реального кінцевого оснащення зберегти чинні ×3/×1, поділ часу всередині одного кадру, bounds/water clipping, bite reaction та правила доступності спорядження. Fight-control під час виважування не змінювати.
6. Класифікація враховує вкладені компоненти та не спирається на назву предмета, DOM, DEV-флаг або одиничний `itemId`. Профіль/коефіцієнти передавати конфігурацією; не дублювати writable equipment-state.

**Критерії приймання:**

- [ ] Детермінований cast лише з rod/reel/line: за однакового input швидкість до й після натягу однакова; для базових налаштувань і `dt=50 ms` вільний від меж рух дає 15 px.
- [ ] Та сама сцена зі справжнім оснащенням зберігає 15 px при slack і 5 px при повністю натягнутій лісці за `dt=50 ms`.
- [ ] Кадр, що перетинає межу slack/натяг, не має зайвого стрибка; довгий кадр підпорядковується чинному `maxDtMs`.
- [ ] Кінець ліски не виходить за воду/бюджет довжини, release зупиняє рух, повторний cast очищає попередній профіль.
- [ ] Одягнений компонент та такий самий компонент лише в рюкзаку дають різну класифікацію; вкладений компонент не помилково вважається порожнім оснащенням.

**Перевірки:** розширити `utils/cast-rod-control-check.js`, `utils/tackle-line-limit-check.js`, `utils/rod-side-tension-check.js` та inventory cast contracts; gameplay suite й game-cycle. Власник: `index.html`/`dev.html` → cast без оснащення → рух вудки до натягу й назад; повторити зі спорядженою снастю, portrait і landscape. Оцінку відчуття руху виконує власник.

## TK-007. Горизонтальні жести вкладок у широкому інвентарі

**Мета:** широкий/landscape інвентар підтримує перехід між розділами та жести вкладок редактора як пальцем, так і затиснутою лівою кнопкою миші. Уточнення власника v0.43.1 поширює задачу на огляд/список рюкзака й садка; попереднє обмеження лише редактором скасовано.

**Зараз у коді:** [InventoryEditorTabsRenderer](src/game/presentation/inventory/inventory_editor_tabs_renderer.js) уже підключає [SwipePagerController](src/platform/browser/dom/swipe_pager_controller.js) до панелі параметрів і прев'ю, а [HorizontalScrollController](src/platform/browser/dom/horizontal_scroll_controller.js) — до ряду вкладок. [inventory_ui_bootstrap.js](src/bootstrap/production/inventory_ui_bootstrap.js) їх компонує; окремий CSS-прапорець `--inventory-editor-swipe: on` заданий у `styles/inventory/modal.css` для всіх розкладок. CSS редактора вже має `touch-action: pan-y`; row має `overflow-x: auto`. Отже загального контракту «тільки вузькі екрани» тут немає: перед виправленням визначити, де саме в wide-жесті втрачаються події/capture або немає overflow.

**Два окремі очікувані сценарії:**

| Початок жесту                             | Результат                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------- |
| Огляд або список у широкому «Рюкзаку»     | Вліво — «Садок», вправо — «Екіпіровка», без вибору прихованої portrait-сторінки |
| Огляд або список у широкому «Садку»       | Вправо — «Рюкзак»; свайп за останній розділ не створює іншого переходу          |
| Ряд вкладок, якщо він ширший за контейнер | Прокрутити ряд горизонтально; не перемикати активну вкладку лише через drag     |
| Прев'ю або панель параметрів              | Перемкнути активну вкладку після завершеного горизонтального swipe              |
| Вертикальний рух у редакторі              | Нативно прокрутити редактор по вертикалі                                        |
| Коротке натискання вкладки без drag       | Відкрити цю вкладку за чинним tap-контрактом                                    |

**Вимоги:**

1. Забезпечити обидва горизонтальні сценарії для mouse і touch незалежно від portrait/landscape чи ширини. Не вимагати wheel або Shift+wheel для миші. Нативну touch-інерцію рядка можна зберегти; повної однаковості фізики інерції не потрібно.
2. Зберегти чинні пороги: row drag — 6 CSS px, початок pager swipe — понад 8 CSS px, commit — щонайменше 20% фізичної ширини swipe-поверхні. Не додавати іншу швидкість/пороги лише для широких екранів.
3. Один жест має одного власника. Row-drag не запускає pager батьків, а editor-swipe — навігацію розділів inventory чи браузера. Поза редактором section swipe доступний в усіх розкладках. Вкладений pager списку у wide передає жест розділам, у portrait зберігає чинний ланцюжок сторінок. Для overview commit рахується від початкової колонки, а не сумарної ширини двох колонок.
4. Після drag не активувати картку/вкладку випадковим click; звичайний tap, long press заповненої комірки та Left/Right/Home/End працюють як раніше. На першій/останній вкладці не переходити за межі й не міняти предмети місцями.
5. Зберегти нативну вертикальну прокрутку та правильний фізичний/логічний перерахунок нижче 320 px. Pointer-capture/cancel, resize й перебудова editor-root не залишають активний drag. Повторне відкриття не множить handlers.
6. Спершу додати регресійний сценарій конкретного збою. Якщо причина в спільному scroll/pager controller, виправляти там і прогнати інших його споживачів; не копіювати контролер у редактор і не прибирати архітектурні перевірки.

**Критерії приймання:**

- [x] У широкому режимі один свайп по рюкзаку перемикає розділ у потрібному напрямку; із садка можна повернутися вправо. Повернення з portrait із запам'ятованою другою сторінкою не додає зайвого кроку.
- [x] У wide/landscape ряд із достатньою кількістю вкладок рухається в обидва боки мишею й touch; без overflow drag не створює фальшивої прокрутки.
- [x] Swipe прев'ю/параметрів перемикає рівно одну сусідню вкладку після commit, коротший жест залишає поточну.
- [x] Вертикальний scroll, click, long press та keyboard-навігація залишаються працездатними; випадкового спорядження після swipe немає.
- [x] Після cancel, resize та п'яти повторних відкриттів один жест обробляється один раз.

**Перевірки:** розширити `utils/inventory-ui-check.js` (широкий layout, обидва pointerType), `utils/platform-runtime-check.js`; за зміни спільного controller — також House/navigation та UI-components checks. Власник: широкий viewport `index.html`/`dev.html` → редактор із переповненим рядом вкладок → mouse-drag рядка, swipe прев'ю, вертикальний scroll; повторити пальцем у landscape.

### TK-008.3. Комп'ютер: hover, область утримання, вибір

- [ ] При дозволеному desktop hover `pointerenter` кнопки розкриває три секції; сам hover **не відкриває** жоден розділ інвентарю. Click по центральній кнопці не вибирає випадковий розділ.
- [ ] Разом із секціями активується **прозора область утримання**: чверть диска під віялом, включно з проміжками й шляхом від центральної кнопки до секцій. Вона не змінює вигляд і не є fullscreen-перекриттям. Поки курсор у цій області, на кнопці або секціях, меню відкрите. Перетин межі дочірнього елемента чи зазору не запускає складання.
- [ ] Наведення на секцію виділяє її; click викликає рівно один `openSection(sectionId)` та складає селектор. Відкривається обраний розділ навіть якщо до цього був активний інший. Повторний вибір цього самого розділу не закриває інвентар.
- [ ] Вихід за всю область утримання без вибору запускає складання; відкладеного автоматичного вибору немає. Після вибору hover не відкриває віяло знову через залишений на тому самому місці курсор: нове hover-розкриття можливе після виходу/повторного входу.
- [ ] Використати `UiSurfaceAdapter.hoverEnabled` і `ui-surface--desktop-hover`: hover діє тільки за спільною політикою (>1024 px, landscape, fine hover, без touch/coarse). На вузькому desktop, у portrait і на touch-ноутбуці миша має доступний press/move/release fallback із TK-008.4 та клавіатуру. Якщо hover стає недоступним під час resize, hover-меню закривається.

### TK-008.4. Телефон: утримання, рух, відпускання

Початкова конкретизація «утримувати»: секції відкриваються на `pointerdown` центральної кнопки й залишаються відкритими, поки цей pointer натиснутий; додаткового очікування long-press у 300/1000 ms немає.

| Подія                                                          | Очікувана дія                                                                            |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Натиснути центральну кнопку й тримати                          | Розгорнути віяло, захопити один active pointer; інвентар поки не відкривати              |
| Вести палець у видиму секцію, не відриваючи                    | Підсвітити поточного кандидата за геометрією сектора; нічого не відкривати               |
| Пройти з однієї секції в іншу                                  | Перенести підсвічування, попередній кандидат не запам'ятовується як вибір                |
| Відпустити в секції                                            | За координатами release визначити ID, один раз виконати `openSection(id)`, скласти віяло |
| Відпустити над центральною кнопкою, в зазорі або поза секціями | Скласти без вибору; раніше підсвічена секція не відкривається                            |
| Отримати `pointercancel` / неочікуваний `lostpointercapture`   | Скасувати жест без вибору та звільнити ресурси                                           |

- [ ] Розпізнавання сектора працює з pointer capture: target captured-події не визначає кандидата; координати переводяться через чинну UI-поверхню. Hit-test відповідає секторам і заокругленням, а не їхнім прямокутним bounding boxes. Прозора keep-open область не є selectable-секцією.
- [ ] Під час анімації не вибирати ще невидиму область: hit-test має відповідати поточному видимому положенню або починатися після розгортання. Release до готовності доступної секції безпечний і нічого не вибирає.
- [ ] Другий палець і неосновні mouse-кнопки ігноруються. Жест селектора не закидає вудку, не рухає камеру, не прокручує/масштабує сторінку й не відкриває native context menu. `touch-action` обмежити компонентом, не вимикати scroll у всій грі.
- [ ] Завершення жесту поглинає його сумісний/synthetic click, тому немає подвійного відкриття чи негайного toggle-close. Release capture, cancel, blur, приховування екрана та dispose не породжують selection.

### TK-008.5. Доступність, ownership і перевірки

- [ ] Центральна кнопка має accessible name «Інвентар», `aria-expanded` і зв'язок із секціями; кожна секція — семантична кнопка з назвою відповідного розділу. Приховані секції недоступні для фокусу, input і accessibility tree. Декоративний SVG/арт не дублює озвучення.
- [ ] Клавіатура: Enter/Space на центральній кнопці відкриває групу, фокус переходить на першу секцію; Tab/Shift+Tab проходять по секціях, Enter/Space вибирає, Escape закриває з поверненням фокусу. Вихід фокусу за компонент закриває його без вибору. Після вибору фокус переходить у відкритий inventory за чинним контрактом; другого modal/focus trap немає.
- [ ] Presentation-компонент володіє лише DOM та станом розкриття/кандидата; browser controller — pointer/keyboard/capture та подіями життєвого циклу. Gameplay-стан і фактичний активний розділ залишаються в чинних власників. Selector передає команди через callbacks, не копіює inventory model і не змінює його state напряму.
- [ ] При mode switch, resize/зміні орієнтації, відкритті іншого modal/екрана, blur, приховуванні сторінки та dispose скасувати незавершений вибір. Відкриття inventory ховає віяло; компонування шарів не піднімає toolbar поверх чужого modal. Pointer capture, listeners, підписки, timers/animation callbacks звільняються; після 10 перемикань режиму один жест дає одну команду.
- [ ] Без постійного другого animation loop, DOM-вимірювань кожного frame та перебудови inventory на pointermove. Межі/перетворення кешуються на жест і перевіряються при resize. Із закритим селектором прозора зона не перехоплює події над грою.
- [ ] Додати production-приклад селектора до `ui-catalog.html`: closed/open, три highlighted-секції, classic/radial, reduced motion. Каталог використовує той самий renderer/controller, без копії макета чи тестової логіки вибору.
- [ ] Автоматизувати desktop-прохід кнопка → зазор → кожна секція → зовнішня область; click відкриває лише потрібний ID. Для touch/mouse fallback перевірити всі три release-вибори, перехід між кандидатами, release поза/в зазорі/в центрі, cancel/lost capture, extra pointer та synthetic click.
- [ ] Перевірити live classic ↔ radial з відкритим і закритим inventory, з активним editor, import/export/reset і відсутнім полем у старих overrides; не дублюються shortcut, state, listeners чи команди. Classic-регресії залишаються чинними.
- [ ] Покрити геометрію/координати на 240/280/319/320 px, 1024/1025 px, portrait/landscape та hybrid touch; кути секторів, зазори, safe area і resize під час hold. Не міняти inventory/keepnet column counts або game-cycle baseline заради нового активатора.

**Рекомендовані межі файлів:** окремі presentation renderer/config/labels і CSS селектора; browser gesture controller у `src/platform/browser/dom/`; композиція в `inventory_ui_bootstrap.js` та за потреби окремому bootstrap-модулі. Локально змінюються shortcut-частини `InventoryUI`/`KeepnetSectionView`, toolbar placement, runtime config/schema/DEV metadata, preload і catalog composition. Назви нових файлів — після перевірки існуючих відповідників; не створювати catch-all UI manager чи загальну систему радіальних меню заради одного компонента.

**Перевірки реалізації:** розширити `inventory-ui`, `inventory-integration`, `keepnet`, `ui-components`, `ui-catalog`, `config-runtime`, `config-schema`, `devtools-links`, `asset-preloader`, `css-usage` з чинного manifest. Додати focused interaction check, якщо сценарії селектора не вкладаються в наявні; підключити до manifest. Далі Architecture + Quick + Full, save round-trip та game-cycle без неочікуваних змін. На цьому етапі документації ці UI-перевірки є планом, а не доказом реалізації.

**Власницьке приймання після реалізації:**

1. `dev.html`, ПК landscape >1024 px без touch → DevTools → увімкнути radial → навести на центральну кнопку, пройти через проміжки, вибрати кожну з трьох секцій; перевірити однакові відступи/радіуси, поворот картинок і плавність розкриття/складання за референсами.
2. `dev.html`, телефон portrait/landscape → натиснути й тримати, провести до кожної секції та відпустити; окремо відпустити в центрі/зазорі/зовні. Перевірити одне правильне відкриття, safe area й короткий landscape; під час жесту гра не реагує.
3. `dev.html` → переключити classic/radial із відкритим редактором, виконати import/reset, змінити орієнтацію під час hold. Переконатися, що старі кнопки відновлюються, а inventory state не втрачається.
4. `index.html` → classic без регресій; `ui-catalog.html` → обидва стани нового компонента, keyboard/reduced motion, ширини 320 і 280 px. Новий production-режим перевірити через інжектовану конфігурацію. Візуальні перевірки й телефонний performance overlay за docs/rendering виконує власник.

## Перевірки й визначення готовності кожної зміни

1. Написати/уточнити відтворення та цільові критерії конкретної задачі. Наявний check, який описує навмисно змінений контракт, оновлювати разом із вимогами, а не видаляти перевірку.
2. Запустити перелічені в задачі focused checks, потім `npm run check:architecture`, `npm run check:quick` і `npm run check` (повний набір). Для inventory-сценаріїв доступний `npm run check:inventory`, для gameplay — `npm run check:gameplay`. Один check запускається як `node utils/run-checks.js --check <id>`; ідентифікатори дивитися через `npm run check:list` у чинному manifest.
3. Перевірити save round-trip та відсутність неочікуваних game-cycle змін. Для навмисної зміни звіту задокументувати причину й оновити baseline у тому самому коміті; DOM-зміни самі по собі не є причиною міняти gameplay-baseline.
4. Перевірити всі реальні споживачі зміненого спільного компонента, а приклади каталогу будувати з production-компонентів. Не залишати замінені мертві tools/fixtures; перед видаленням довести відсутність consumers. Live checks без рішення власника не видаляти.
5. Синхронізувати версію у `project_version.js`, `package.json`, `package-lock.json`, `?v=` трьох HTML-сторінок та додати CHANGELOG. Нові service-артефакти зберігати лише в `utils/tmp/` або `utils/generated/`, після роботи виконати `npm run clean:artifacts`.
6. Передати власнику короткі кроки приймання саме зміненого сценарію з колонкою сторінка/орієнтація. **Візуальні browser-smoke, порівняння та play-check виконує власник**; у звіті агента прямо зазначити, що візуальна перевірка не виконувалася. Для rendering-змін власник додатково вимірює продуктивність на телефоні в обох орієнтаціях за docs/rendering.

Для responsive-приймання використати 240, 280, 319, 320 px і ширші екрани, portrait/landscape; окремо mouse, touch і hybrid. Задача готова, коли виконані її критерії, automated checks пройдені, зміна має версію, а власник виконав відповідне візуальне/ігрове приймання. Незаповнений початковий розділ «Виконано» не переноситься як доказ завершення.
