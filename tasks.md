## Спільні вимоги до реалізації

- Дотримуватися [DEVELOPMENT_RULES.md](DEVELOPMENT_RULES.md), [DESIGN_RULES.md](DESIGN_RULES.md), [docs/styles.md](docs/styles.md), [docs/inventory-behavior.md](docs/inventory-behavior.md); для прицілу, сцени й HUD — також [docs/rendering.md](docs/rendering.md).
- Application володіє переходами та сценаріями, Domain — правилами; presentation відображає стан, platform обробляє браузерні події. Конкретні реалізації, scheduler і конфігурація компонуються в bootstrap. Не додавати глобали чи залежності production → DEV.
- Факти про предмети, оснащення, час і позицію вудки мають одного чинного власника. Не створювати їхні writable-копії в DOM, renderer або DEV.
- Зберігати логічну композицію 320 px і єдине масштабування нижче неї; інвентар — 4 мобільні колонки, садок — 2. Не змінювати ці сітки заради локальної задачі.
- Використовувати чинні BEM-блоки, семантичні токени, видимий keyboard focus, `prefers-reduced-motion` і спільну політику hover. Статичне оформлення належить CSS.
- Підписки, timers, pointer capture та observers звільняти разом із власником. Не додавати постійний другий цикл анімації, DOM-вимірювання щокадру або перебудову всього інвентаря на pointermove.
- Перед виправленням зафіксувати відтворення та очікуваний результат. Для gameplay-змін додати окремі записи до [docs/gameplay_backlog.md](docs/gameplay_backlog.md). Для нової або зміненої механіки перед кодом оформити feature-spec у `specs/` за поточною нумерацією.
- Структурні зміни, якщо необхідні, відокремити від зміни поведінки. Не оновлювати baseline, guards чи whitelists лише заради зелених перевірок. Game-cycle baseline змінювати тільки для поясненої зміни результату в тому самому gameplay-коміті.
- Кожна доставлена зміна має версію та CHANGELOG. За вказівкою власника від **2026-10-20** збільшувати лише patch; середню частину (minor) не змінювати до його прямої команди, навіть для нової/зміненої механіки.

## Перевірки й визначення готовності кожної зміни

1. Написати/уточнити відтворення та цільові критерії конкретної задачі. Наявний check, який описує навмисно змінений контракт, оновлювати разом із вимогами, а не видаляти перевірку.
2. Запустити перелічені в задачі focused checks, потім `npm run check:architecture`, `npm run check:quick` і `npm run check` (повний набір). Для inventory-сценаріїв доступний `npm run check:inventory`, для gameplay — `npm run check:gameplay`. Один check запускається як `node utils/run-checks.js --check <id>`; ідентифікатори дивитися через `npm run check:list` у чинному manifest.
3. Перевірити save round-trip та відсутність неочікуваних game-cycle змін. Для навмисної зміни звіту задокументувати причину й оновити baseline у тому самому коміті; DOM-зміни самі по собі не є причиною міняти gameplay-baseline.
4. Перевірити всі реальні споживачі зміненого спільного компонента, а приклади каталогу будувати з production-компонентів. Не залишати замінені мертві tools/fixtures; перед видаленням довести відсутність consumers. Live checks без рішення власника не видаляти.
5. Синхронізувати версію у `project_version.js`, `package.json`, `package-lock.json`, `?v=` трьох HTML-сторінок та додати CHANGELOG. Нові service-артефакти зберігати лише в `utils/tmp/` або `utils/generated/`, після роботи виконати `npm run clean:artifacts`.
6. Передати власнику короткі кроки приймання саме зміненого сценарію з колонкою сторінка/орієнтація. **Візуальні browser-smoke, порівняння та play-check виконує власник**; у звіті агента прямо зазначити, що візуальна перевірка не виконувалася. Для rendering-змін власник додатково вимірює продуктивність на телефоні в обох орієнтаціях за docs/rendering.

Для responsive-приймання використати 240, 280, 319, 320 px і ширші екрани, portrait/landscape; окремо mouse, touch і hybrid. Задача готова, коли виконані її критерії, automated checks пройдені, зміна має версію, а власник виконав відповідне візуальне/ігрове приймання.
