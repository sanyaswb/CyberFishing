# 1. Invariants

```text
OBSERVATION = FACTS

CLASSIFICATION = ARCHITECTURAL DECISION
```

- Build a reliable dependency graph first, then classify ownership, and only then move files.
- Do not infer architectural ownership from a filename, current directory, or class suffix.
- Do not change fishing physics, inventory, items, progression, UI behavior, save format, or game-state semantics during architecture tasks.
- Do not create a runtime dependency scanner, runtime architecture validator, or permanent dynamic script loader.
- Do not add a global or an architecture exception merely to make a check pass.
- Keep each subsequent task to one small dependency cluster, with relevant tests and a manifest update.
- Do not mix ESM conversion with opportunistic API, formula, or behavior refactoring.
- Keep repository tooling in `utils/` unless a separate task justifies moving it.
- Use OOP as the default style, but prefer composition over inheritance; do not introduce artificial class hierarchies for pure calculations or value transformations.
- Give each mutable game-state fact one authoritative owner. Explicitly mark cached or derived state and never treat it as a second source of truth.
- Keep Domain contracts independent of `game/config`; inject raw configuration through constructors, factories, or the composition root.
- Base performance decisions on evidence: hot-loop participation, allocation frequency, DOM/Canvas access, and profiling risk. Add object pooling only for a proven high-churn lifecycle.

```text

├── assemblies/

src/game/application/  orchestration, not Domain ownership
```

Reviewed Manifest metadata determines target paths, not current directory names. Add a new subdomain only after classification and policy review.

Domain must not depend on platform, UI, Canvas, DOM, dev, or raw configuration. Inject configuration through constructors, factories, or the composition root. Domain may depend only on stable engine primitives and its own Domain contracts or value objects.

# 7. Transitional compatibility rules

If a dependency cluster cannot be migrated atomically, a temporary `compat/` or `legacy_bridge/` is allowed.

Bridges must not contain:

```text
business logic
new domain behavior
permanent APIs
```

Every bridge must have an owner, a reason, and a `removalStage`.

---

# 8. When to Stop

Make a separate architecture decision if a change would:

```text
add another global
allow engine → game dependencies
allow domain → document/window dependencies
load legacy scripts from a new entrypoint
rewrite a gameplay class solely for ESM conversion
ignore a file because an architecture check blocks it
expand a baseline solely to make a check pass
```

Do not bypass these cases with a workaround; review the dependency design.
