# CyberFishing — актуальний план незавершеного модульного рефакторингу

**Stage 1 closure-версія:** `v0.24.31`  
**Тип робіт:** architecture / infrastructure refactoring  
**Gameplay changes:** заборонені  
**Поточний наступний етап:** `Stage 2.0 — Classic Bridge Build Foundation`

Цей документ містить тільки роботи, які ще не виконані.

---

# 1. Незмінні принципи

```text
OBSERVATION = FACTS

CLASSIFICATION = ARCHITECTURAL DECISION
```

- Спочатку будуємо достовірний dependency graph, потім класифікуємо і лише після цього переносимо файли.
- Не визначати architecture ownership за filename, поточною папкою або суфіксом класу.
- Не змінювати fishing physics, inventory, items, progression, UI behavior, save format або game-state semantics у межах architecture tasks.
- Не створювати runtime dependency scanner, runtime architecture validator або постійний dynamic script loader.
- Не додавати новий global чи architecture exception лише для того, щоб зробити check зеленим.
- Кожна наступна задача має охоплювати один невеликий dependency cluster разом із tests і manifest update.
- Не змішувати ESM conversion з opportunistic API, formula або behavior refactoring.
- Repository tooling залишається в `utils/`, доки окрема задача не обґрунтує path migration.

# 2. Stage 2 — Engine / low-level modules

Authoritative execution specification:

```text
architecture/migration/stage_2_approved_batches.json
```

Поля `files`, `target paths`, `dependency ordering`, `bridge strategy`,
`removalStage`, `tests`, `architecture gates`, `rollback boundary` та
`acceptance criteria` вже frozen і не проєктуються повторно під час реалізації.

## Stage 2.0 — Classic Bridge Build Foundation

- [ ] Додати build runner, який збирає тільки active approved ESM bridge wrappers.
- [ ] Генерувати synchronous classic IIFE outputs у `dist/legacy-bridges/`.
- [ ] Не робити `index.html` Vite entrypoint і не включати весь game graph у build.
- [ ] Валідувати exact bridge registry records та exact global providers.
- [ ] Інтегрувати build у dev-server як fail-fast prerequisite.
- [ ] Довести deterministic output, cleanup/ignore semantics і empty-registry no-op.
- [ ] Запустити focused check, Architecture, Quick, All та browser smoke.

## Approved dependency-safe batches

Виконувати строго послідовно:

```text
Stage 2.0 bridge build foundation
    ↓
Stage 2.1 engine asset contracts
    ↓
Stage 2.2 engine dependency contract
    ↓
Stage 2.3 engine event primitives
    ↓
Stage 2.4 engine rendering primitives
```

Почати реальний ESM-перехід із затверджених pure/leaf low-level modules.
Кожен batch є окремим atomic cutover із власним rollback boundary.

## Подальший Engine scope

Почати реальний ESM-перехід dependency-safe batches із pure/leaf і low-level modules:

```text

```

Для кожного batch визначити current files, target files, imports, exports, consumers, temporary compatibility, tests та acceptance criteria.

- очистити legacy `systems/services/app` structure;
- виконати production hardening.

# 8. Transitional compatibility rules

Якщо dependency cluster неможливо мігрувати атомарно, дозволений тимчасовий `compat/` або `legacy_bridge/`.

У bridge заборонені:

```text
business logic
new domain behavior
permanent APIs
```

Кожен bridge повинен мати owner, reason і `removalStage`.

---

# 9. Коли потрібно зупинитися

Потрібне окреме architecture рішення, якщо пропонується:

```text
додати ще один global
дозволити engine → game
дозволити domain → document/window
завантажити legacy scripts із нового entrypoint
переписати gameplay class лише для ESM conversion
додати файл у ignore, бо architecture check заважає
розширити baseline лише для зеленого check
```

Такі ситуації не обходяться workaround — переглядається dependency design.
