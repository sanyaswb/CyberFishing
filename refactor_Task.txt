# 1. Незмінні принципи

```text
OBSERVATION = FACTS

CLASSIFICATION = ARCHITECTURAL DECISION
```

- Спочатку будуємо достовірний dependency graph, потім класифікуємо і лише після цього переносимо файли.
- Не визначати architecture ownership за filename, поточною папкою або суфіксом класу.
- Не змінювати fishing physics, inventory, items, progression, UI behavior, save format або game-state semantics у межах architecture tasks.
- Не створювати runtime dependency scanner, runtime architecture validator або постійний dynamic script loader.
- Не додавати новий global чи architecture exception лише для того, щоб зробити check зеленим.
- Кожна наступна задача має охоплювати один невеликий dependency cluster разом із tests і manifest update.
- Не змішувати ESM conversion з opportunistic API, formula або behavior refactoring.
- Repository tooling залишається в `utils/`, доки окрема задача не обґрунтує path migration.
- OOP є базовим стилем, але composition має перевагу над inheritance; pure calculations і value transformations не отримують штучних class hierarchies.
- Кожна частина mutable game state повинна мати одного authoritative owner; cached/derived state позначається явно і не стає другим source of truth.
- Domain contracts не залежать від `game/config`; raw configuration надходить через constructor injection, factories або composition root.
- Performance-рішення приймаються за evidence: hot-loop participation, allocation frequency, DOM/Canvas access і profiling risk. Object pooling не додається без доведеного high-churn lifecycle.

# 2. Stage 3 — Game Domain

## Цільова структура

```text
src/game/domain/
├── assemblies/
├── casting/
├── equipment/
├── fish/
├── fishing/
├── inventory/
├── items/
├── line/
├── loadouts/
├── locations/
├── rules/
└── tackle/

src/game/config/       external щодо domain
src/game/application/  orchestration, не domain ownership
```

Цільові paths визначаються reviewed Manifest metadata, а не назвою поточної папки. Новий піддомен додається лише через classification/policy review.

Domain не залежить від platform, UI, Canvas, DOM, dev або raw configuration. Configuration надходить через constructor injection, factories або composition root. Domain може залежати лише від стабільних engine primitives і власних domain contracts/value objects.

## Stage 3.5–3.21 — Atomic Domain Migration Batches

Завершено чотири frozen batches: `4/21` batches, `4/69` frozen domain-модулів. Наступний exact batch:

```text
stage-3.candidate-005-fishing-45d0c7ce

6 fishing domain modules
7 activation contracts

positions: 93, 117 (2 symbols), 118, 122, 128, 133
```

Batch 005 є першим multi-module Stage 3 cluster. Усі шість модулів мігруються атомарно відповідно до frozen internal dependency topology; partial cutover заборонений.

Кожен approved batch проходить один повторюваний pipeline:

```text
preflight
→ named ESM targets
→ exact temporary classic bridges
→ Manifest + observations
→ architecture guards
→ focused behavior/state/performance checks
→ Quick + Architecture + Full
→ fresh npm ci acceptance
→ browser smoke
→ release + rollback boundary
```

Stage 3 завершується, коли всі approved domain batches перенесені, domain boundary не має залежностей на platform/UI/Canvas/DOM/dev/config, state ownership однозначний, а тимчасові bridges мають контрольований removal path.

# 6. Stage 7 — Structural Hardening

Після стабільного ESM:

- декомпозувати великі mixed-responsibility classes;
- остаточно розділити engine/game/platform/dev;
- видалити transitional compatibility code;
- очистити legacy `systems/services/app` structure;
- виконати production hardening.

---

# 7. Transitional compatibility rules

Якщо dependency cluster неможливо мігрувати атомарно, дозволений тимчасовий `compat/` або `legacy_bridge/`.

У bridge заборонені:

```text
business logic
new domain behavior
permanent APIs
```

Кожен bridge повинен мати owner, reason і `removalStage`.

---

# 8. Коли потрібно зупинитися

Потрібне окреме architecture рішення, якщо пропонується:

```text
додати ще один global
дозволити engine → game
дозволити domain → document/window
завантажити legacy scripts із нового entrypoint
переписати gameplay class лише для ESM conversion
додати файл у ignore, бо architecture check заважає
розширити baseline лише для зеленого check
```

Такі ситуації не обходяться workaround — переглядається dependency design.
