Скласти план покращеного завантаження скриптів для запуску гри, пройтися по spec 157, дати пропозицію й очікуваний приріст;

Заміри, цілі й перелік завдань закриття — один результат у [spec 157](../157-startup-load-optimization/spec.md), тут вони не повторюються.

## Пропозиція

### Етап 1. Лише збірка релізу (низький ризик)

1. **Один файл стилів у релізі** замість 32: мінус 31 запит і ~24–33 КБ. `?esm=1` і локальна робота без змін.
2. **Один стартовий шматок JS:** статичні імпорти замість динамічних для стартових дрібниць (`START_IMPORTS`): з 20 файлів JS
   до ~8. Це й закриває ціль хвиль ≤ 3 зі spec 157.
3. **Журнал релізів поза стартом:** перевірити споживачів `notes`; лише DEV → перенести в DEV. Мінус 13 КБ gzip.

### Етап 2. Інвентар після першого кадру (погоджено власником)

UI інвентаря й садка компонується й вантажиться після `ready` через `LazyFeature`, кнопка до приходу працює (перша дія чекає).
Мінус ~56 КБ gzip і більшість етапу `inventory`. Спершу CPU-профіль етапів `inventory` і `location` (TK-176 п. 3).
Ризик: довга задача одразу після першого кадру; її треба ділити на частини.

### Не пропоную

- **Бій окремим шматком (~70 КБ):** лише ~0.35 с на повільній мережі, а ризик для `composeFishingServices`, game-cycle і
  першого кльову реальний.
- **Service worker і кеш між релізами (R7, Q2):** лише теплий старт, а головна метрика власника — холодний.
- **Воркери:** окрема спека після 157, спершу профіль (рішення власника 2026-10-31).
- **Brotli:** на Pages неможливий; додати у вимоги власного сервера (`docs/deployment.md`): мінус ~20 % JS без зміни коду.

## Поправка етапу 1 (заміри)

Четверту хвилю давав не JS: JS уже йшов двома кроками (`moduleSteps` 2). Ланцюг на Fast 4G був `index.html` → бандл → `test-depth.webp` →
`float-day-glow.webp`: групи першого шару плану чекали одна одну за пріоритетом (`location` 1, решта 2). Тепер у всіх груп першого шару один пріоритет.
Результат JS: 20 → 10 файлів, а не ~8: лишаються дрібні шматки, які esbuild ділить із лінивими функціями.

## Профіль етапу 2

v0.49.86 (`a701b2de`), Chrome headless, телефон 412×915, `--cpu 4`, середнє 3 холодних запусків, час функцій з картою коду.

| Що | Час на `--cpu 4` |
| --- | --- |
| Етап `inventory` усього | 288 мс |
| — `#composeInventoryUi` (усе, що може поїхати) | **124 мс** |
| — з них перший `refresh()` закритого інвентаря | 80 мс (модель вигляду 26, рендер 54) |
| — з них садок / селектор (селектор лишається: він у першому кадрі) | 11 / 13 мс |
| — `#composeWorldSystems` | 113 мс |
| — `#composePlayerInventory` | 33 мс |
| Етап `location`: `getImageData` карти глибин | 89 мс |

| Припущення spec 160 | Заміряно |
| --- | --- |
| ~200 мс CPU переїдуть за перший кадр | **~110 мс** (124 мінус селектор) |
| мінус ~56 КБ gzip | **мінус ~34 КБ gzip** (126 КБ мінімізовано, 39 модулів: граф без `inventory_ui_bootstrap`); модель вигляду й її резолвери потрібні фасаду інвентаря й лишаються |

Перерахований приріст етапу 2 проти оцінки:

| Умови | Оцінка | За профілем |
| --- | --- | --- |
| Slow 4G, `--cpu 4` | ~0.45 с | **~0.28 с** (34 КБ ≈ 0.17 с мережі + 0.11 с CPU) |
| Fast 4G, `--cpu 4` | ~0.2 с | **~0.14 с** |
| Fast 4G, ПК | ~0.08 с | ~0.05 с: менше за розкид вимірювача |

Те, що переїде, не зникає: ~110 мс на `--cpu 4` стануть задачею після першого кадру, де вже є довга задача Pixi (565–583 мс, ~1.7 с від старту) і ще одна на ~0.43 с (412–504 мс, сама композиція).
Перша дія гравця з інвентарем також чекатиме модуль.

**Дешевша альтернатива, яку показав профіль:** не робити перший `refresh()`, поки інвентар закритий (`open()` і так робить `refresh()`): до ~80 мс на `--cpu 4` без нового шматка й без очікування на тап. Байтів не зменшує.

**Рішення власника (2026-11-05): дешевий варіант, TK-213, v0.49.92.** `mount()` не малює закритий інвентар; `onReady` радіо й редактора оновлюють його лише відкритим. Лінивого шматка немає.

| T-play, холодний, медіана 3 запусків | v0.49.90 | v0.49.92 | Етап `inventory` |
| --- | --- | --- | --- |
| Fast 4G, ПК | 807 мс | 801 мс | 46 → 34 мс |
| Fast 4G, `--cpu 4` | 1306 мс | 1219 мс | 249 → 184 мс |
| Slow 4G, `--cpu 4` | 3399 мс | 3347 мс | 246 → 178 мс |
| Без обмеження мережі, `--cpu 4` | 894 мс | 811 мс | 248 → 180 мс |

Доказ — етап `inventory` (мінус ~65 мс на `--cpu 4`); різниця T-play менша за розкид вимірювача. Ціна: перше відкриття інвентаря тепер малює список само (оцінка за профілем до ~54 мс на `--cpu 4`, окремо не заміряно). Зміна вмісту інвентаря при закритому вікні, як і раніше, малює його одразу.
