# Spec 160. Завантаження скриптів на старті й закриття spec 157 (TK-204)

Статус: етап 1 погоджено (покращення бандла, власник); етап 2 чекає рішення власника.

## Запит власника (2026-11-05)

Скласти план покращеного завантаження скриптів для запуску гри, пройтися по spec 157, дати пропозицію й очікуваний приріст;
повністю завершити spec 157.

## Вихідні дані

Заміри, цілі й перелік завдань закриття — один результат у [spec 157](../157-startup-load-optimization/spec.md), тут вони не повторюються.

Склад стартового шматка (1285 КБ мінімізовано, 350 КБ gzip, 279 КБ brotli, 615 модулів):

| --- | --- | --- | --- |
| Бій (домен і застосунок) | 256 КБ | ~70 КБ | частка в шматку |
| UI інвентаря | 182 КБ | ~50 КБ | частка в шматку |
| Прикормка й кораблик (застосунок) | 32 КБ | ~9 КБ | частка в шматку |

Стилі: 32 файли 43.8 КБ gzip, один мінімізований файл 19.6 КБ gzip (реальна збірка).

## Пропозиція

### Етап 1. Лише збірка релізу (низький ризик)

1. **Один файл стилів у релізі** замість 32: мінус 31 запит і ~24–33 КБ. `?esm=1` і локальна робота без змін.
2. **Один стартовий шматок JS:** статичні імпорти замість динамічних для стартових дрібниць (`START_IMPORTS`): з 20 файлів JS
   до ~8. Це й закриває ціль хвиль ≤ 3 зі spec 157.
3. **Журнал релізів поза стартом:** перевірити споживачів `notes`; лише DEV → перенести в DEV. Мінус 13 КБ gzip.

### Етап 2. Інвентар після першого кадру (рішення власника)

UI інвентаря й садка компонується й вантажиться після `ready` через `LazyFeature`, кнопка до приходу працює (перша дія чекає).
Мінус ~56 КБ gzip і більшість етапу `inventory`. Спершу CPU-профіль етапів `inventory` і `location` (TK-176 п. 3).
Ризик: довга задача одразу після першого кадру; її треба ділити на частини.

### Не пропоную

- **Бій окремим шматком (~70 КБ):** лише ~0.35 с на повільній мережі, а ризик для `composeFishingServices`, game-cycle і
  першого кльову реальний.
- **Service worker і кеш між релізами (R7, Q2):** лише теплий старт, а головна метрика власника — холодний.
- **Воркери:** окрема спека після 157, спершу профіль (рішення власника 2026-10-31).
- **Brotli:** на Pages неможливий; додати у вимоги власного сервера (`docs/deployment.md`): мінус ~20 % JS без зміни коду.

CPU-профіль. Приріст етапу 1 менший за розкид вимірювача, тож його доводять байти, запити й хвилі, а не T-play.
