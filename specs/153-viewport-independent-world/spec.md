# Spec 153: світ не залежить від розміру вікна (G-126)

**Створено**: 2026-10-30 · **Статус**: рішення прийняті 2026-10-30; реалізовано v0.50.53 (2026-11-09, власник: «Так беремося за 153 spec»); приймання власником відкрите · **Вид**: виправлення геймплею

## Запит власника (2026-10-30)

Гравець може сам звузити сторінку в браузері й так підсунути поплавок, рибу чи кораблик до центру екрана —
це чит. Продумати, як запобігти; варіант — пауза гри, коли відкриті інструменти розробника, або інший спосіб.

## Причина (за кодом, develop 14bd71e9)

- `CONFIG.locations.lockZoneXToScreen = true` (`game_config.js:231`). `GameWorld.getDynamicBounds()`
  (`game_world.js:61`) тоді бере ліву/праву межу світу з **видимого екрана** (`screenToVirtual(0..canvas width)`), а
  не з карти.
- Ці межі — межі фізики: `WaterEntity._applyPhysics` щокадру затискає позицію поплавка/риби в них
  (`water_entity.js:479`), кораблик відхиляє кожен крок поза ними (`GameWorld.update` → `checkPhysics`). Звузив
  вікно чи панорамував — межа світу посунулась, обʼєкт «переїхав» до видимої частини.
- Ще одне значення бою залежить від ширини екрана: частка бокового відхилення риби від вудки =
  |x риби − x вудки| на екрані / половина ширини canvas (`game_viewport_facade.js:106`).
- Камера стежить лише по Y (`focusOnVirtualPos`); по X світ «тримається» в екрані саме цим затисканням.

## Чому не пауза на інструменти розробника

- У браузері немає API «DevTools відкриті»; евристики (різниця `outerWidth − innerWidth`, таймінги `debugger`)
  дають хибні спрацювання (зум, бічні панелі, відкріплені DevTools не змінюють вікно) і легко обходяться.
- Звузити вікно можна й без DevTools, а поворот телефона чи розділений екран — законна зміна розміру.
- Пауза не прибирає причину: після неї межі все одно звузяться. А хто відкрив DevTools, може змінити будь-яку
  змінну JS — від цього захищає тільки сервер (DEVELOPMENT_RULES: результати улову перевіряє бекенд).

## Пропозиція

**Розмір вікна — лише камера, не світ.** Межі фізики — вода карти (`getCastableBoundsVirtual`), незалежно від
екрана; звуження вікна показує менше, але нічого не рухає.

- **D1 (2026-10-30, власник)** Камера по X стежить за точкою снасті (поплавок, риба в бою), коли вона підходить до
  краю екрана. За корабликом камера **не** стежить.
- **D2 (2026-10-30, власник: так, у метрах)** Бокове відхилення риби рахувати в метрах відносно вудки (від ширини води/дальності), а не від половини
  екрана. Рекомендація: так; крива бою не змінюється для еталонного екрана 2560 px (перевірка game-cycle).
- **D3 (2026-10-30, власник)** Позиція вудки у світі не змінюється від зміни вікна; екран фокусується відносно
  вудки так, щоб її завжди було видно.
- Окремо (не ця спека): серверна перевірка результатів — коли зʼявиться бекенд.

**Власник, 2026-10-30.** Пауза на DevTools — ні. Головна проблема: після кльову край вікна браузера може посувати
саму рибу, і гравець підтягує її, просто звужуючи вікно. Рішення: риба може виходити за межі екрана, а камера
фокусується на ній, щоб вона лишалася в полі зору. Черговість: після завершення всіх виправлень кораблика.

## План реалізації (агент, 2026-11-09)

За кодом (develop 0.50.52) камера вже тримає центр світу при зміні розміру (`ViewportProjector.update`, `centreVirtualX`),
але вудка прив'язана до **центру екрана** (`GameViewportFacade.#resolveBaseRodScreenX` = половина ширини canvas): біля
краю карти камера впирається, і вудка «їде» у світі; а слідування камери по X (D1) теж рухало б її. Тому:

1. **Межі — вода карти.** `GameWorld.getDynamicBounds()` повертає межі карти; налаштування `lockZoneXToScreen` прибрано.
2. **Вудка має якір у світі** (`GameViewportFacade`): екранне X вудки = проєкція якоря. Якір рухається лише разом із
   панорамою гравця (розвідка, приціл прикормки: вудка лишається на тому самому місці екрана, як зараз); після зміни розміру
   камера ставить якір у центр нового canvas (те саме, що spec 098 робить для розділеного інвентарю, тепер для кожної
   зміни розміру). Вудка у світі від розміру вікна не рухається (D3).
3. **Камера по X стежить за снастю** (D1): у очікуванні, клюванні й бою, коли поплавок або риба заходить у крайову смугу
   екрана (`CONFIG.locations.cameraFollowMarginX`, частка ширини), камера плавно зсувається; вудка лишається у кадрі
   (пріоритет), тож риба може вийти за край, якщо вудка інакше вийшла б. За корабликом камера не стежить.
4. **Бокова частка бою** (D2) = |X риби − X вудки| в одиницях карти / половина еталонної ширини
   (`baseResolution.width / 2`): на еталонному екрані 2560 px (масштаб 1) це те саме число, що й зараз, і воно не залежить
   від вікна.
5. Знайдено поза спекою (питання власнику, не в цьому кроці): діапазон бічного руху вудки обмежено краями canvas
   (`RodVisualOffsetSystem.resolveScreenX`, відступ 16 px) — на вузькому вікні вудка ходить вужче.

game-cycle бере фіксовані межі й вудку (`game-cycle-check.js`), тож його звіт не має змінитись.

## Перевірки

Детермінований сценарій: поплавок, риба й кораблик біля краю; канвас звужується вдвічі й панорамується — позиції
у світі й фізика не змінюються, змінюється лише камера. Падає на старому коді. Game-cycle на еталонному розмірі —
без змін або погоджене оновлення.

## Реалізація (v0.50.53)

- `GameWorld.getDynamicBounds()` — межі води карти; `lockZoneXToScreen` прибрано, на його місці
  `CONFIG.locations.cameraFollowMarginX: 0.15`.
- `GameViewportFacade`: якір вудки у світі (`#rodAnchorX`, з налаштованого `ui.rod.x` при першому розміщенні камери, скидається
  при зміні локації); `panByPlayer` (панорама гравця несе вудку разом із камерою); `keepRodAnchored` / `recenterRod` ставлять
  якір на налаштоване місце екрана без зайвої панорами. `GameApplication`: кожна зміна розміру (не лише розділений
  інвентар) тримає вудку на місці у світі.
- `ViewportProjector.followVirtualX(targetX, keepX, dt, marginShare)`: камера по X стежить за поплавком / рибою в
  очікуванні, клюванні й бою, вудка в кадрі — першочергово; без алокацій у кадрі.
- D2: `getScreenOffsetRatio` = |X риби − X вудки| в одиницях карти / (`baseResolution.width` / 2). За кодом ця частка
  йде лише в DEV-діагностику (`getStateDebugData` → `FightService.getDiagnostics`), не в бій; там вона ще й читала вудку,
  затиснуту до x = 16, бо `RodVisualOffsetSystem.resolveScreenX` перетворював відсутню межу (`null`) на 0 — виправлено
  (відсутня межа — без обмеження).
- Інцидент I-18, правило R19 (`docs/incidents.md`); G-126 закрито.
- Перевірки: `viewport` — три розміри вікна (межі карти, X вудки у світі, бокова частка), камера стежить за снастю й
  тримає вудку, панорама гравця; падає зі старим `GameWorld`. Оновлено фейки проєктора (`followVirtualX`) у 5 перевірках,
  `bait-boat-recovery` (межі = карта), `game-application-composition` (перецентрування після зміни розміру; частка D2
  замість старого затискання). Full 85/85, game-cycle без змін (бере фіксовані межі).
- Поза спекою, питання власнику: діапазон бічного руху вудки обмежено краями canvas (`resolveScreenX`, 16 px).
