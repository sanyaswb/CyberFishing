# Spec 157: швидкий старт гри — завантаження й оптимізація

**Створено**: 2026-10-30 · **Статус**: ТЗ, усі рішення власника Q1–Q7 прийнято 2026-10-30; реалізація — у новій сесії · **Вид**: продуктивність, реліз,
завантаження ресурсів · **Задача**: TK-165

## Запит власника (2026-10-30)

Сторінка дуже довго вантажиться (підозра — аудіо). Детально розписати рішення й оптимізацію довгого завантаження з
усіма нюансами, з урахуванням spec, де розписана логіка «розумного» прелоадера.

## Повʼязані специфікації

- **[Spec 047](../047-smart-asset-preloader/spec.md) — Smart asset preloader** (вимоги FR-001…FR-033, план, модель
  даних, контракт рантайму): каталог ресурсів, якісні варіанти `l/m/h/legacy`, черга з пріоритетами
  `blocking > interactive > upgrade > prefetch`, мінімальний стартовий набір, апгрейди після старту, пауза спекулятивних
  завантажень (прихована вкладка, offline, save-data), бюджет памʼяті, Spine опційно.
- **[Spec 083](../083-preloader-foundation/spec.md) — фундамент прелоадера** (реалізовано; у гру підключено лише `AssetLoadQueue` — Spine вудки й кораблика
  через `rod_animation_composition.js` / `boat_animation_composition.js`; **не підключені `StartupLoadProgress`, facade і
  екран завантаження**):
  engine `AssetCatalog`, `AssetVariantSelector`, `AssetLoadQueue`, `StartupLoadProgress`; цільова архітектура старту
  (екран завантаження шаром у `index.html` з першої відмальовки, мінімальний бар'єр, потім апгрейди/prefetch);
  рішення власника 1–6 (екран у `index.html`; Spine = атлас + JSON; **спершу поточна фаза доби**, далі інші як prefetch;
  `full > l > placeholderColor`; постер `assets/ui/loader/loader-poster.webp` + портретний 9:16; порядок фонів).
  Наступні кроки 083 (store + facade, екран завантаження, якість) — саме те, що ця спека доводить до гри.
- [Spec 097](../097-backpack-item-keepnet-art/spec.md) — мініатюри предметів як повнорозмірні 2048 px (рішення про якість; замінено Q3: 1024 px middle, одна картинка на всі місця).
- [Spec 100](../100-render-resolution-and-image-quality/spec.md), [102](../102-render-quality-policy/spec.md),
  [docs/rendering.md](../../docs/rendering.md) — розміри артів «близько 1:1», бюджет текстур, заміри на телефоні.
- [Spec 106](../106-scene-water/spec.md) / 103–105 — сцена Pixi: перший рендер компілює шейдери (90–150 мс, прогрів).

## Цілі та метрики

Вимірюються на телефоні власника (обидві орієнтації не впливають на завантаження — одна достатня), Pages, мережа 4G,
холодний старт (новий реліз) і теплий (повторне відкриття того ж релізу).

**Головна метрика (власник, 2026-10-30): чистий холодний старт без кешу** — гравець, що вперше відкриває гру. Усі
рішення цієї спеки оцінюються саме ним (DevTools «Disable cache» / новий профіль / вимірювач cold); швидкість досягається
розумним порядком і обсягом завантаження, а не кешем. Теплий старт — довідково.

| Метрика | Що означає | Ціль (Q4, власник 2026-10-30) |
| --- | --- | --- |
| T-paint | перша відмальовка екрана завантаження | ≤ 1 с |
| T-play | гра готова до дій (мінімальний бар'єр 083, сцена намалювала перший кадр) | **холодний ≤ 4 с, бажано 3 с** (власник: замість 5 с), теплий ≤ 2 с |
| Bytes-play | **переданих (стиснутих) байтів** до T-play | ≤ 3 МБ (зараз оцінка ~9 МБ+ без стиснення); при 3–4 с на 4G фактично ~2–2.5 МБ — бюджет стартового маніфесту 2.5 МБ **стиснутих** |
| Req-play | запитів до T-play | ↓ (зараз 700+) |
| Waterfall | глибина послідовних мережевих кроків до T-play | ≤ 3 |

**Байти рахуються стиснутими (рішення власника 2026-10-30, після рев'ю спеки).** Pages віддає JS/CSS/JSON зі стисненням
gzip, а мета — час у мережі. Нестиснуті розміри з git бюджет не проходять навіть теоретично: код 2.7 МБ + Pixi 0.8 МБ =
3.5 МБ, тоді як стиснуті — приблизно втричі менше. Тому:
- release-скрипт для кожного файлу маніфесту записує **стиснутий розмір**: JS/CSS/JSON/SVG/атлас — gzip вмісту з git (рівень
  як у типового сервера, напр. 6), картинки WebP і аудіо — розмір файлу як є (вони вже стиснуті);
- бюджет 2.5 МБ і Bytes-play перевіряються за цими стиснутими розмірами; gzip Pages може трохи відрізнятися — бюджет
  оцінковий, з запасом; вимірювач (R9) звіряє з фактичним `transferSize`;
- екран завантаження (R3) показує ті самі стиснуті байти — і знаменник, і чисельник, щоб «МБ / МБ» не змішували
  стиснуте з нестиснутим; нестиснуті розміри — лише в DEV-оверлеї.

Базова лінія (до змін) записується в цій спеці на етапі A.

## Рішення (рекомендації; Q — питання до власника)

### R1. Граф модулів: `modulepreload` без збірки (Q1)

Release-скрипт (`utils/build-pages-release.js`) уже сам обходить граф модулів сторінки (власний обхід через acorn,
`ReleaseFileSet`; не механізм `npm run struct`) — етап B будується на ньому. Він вписує в `index.html`/`dev.html` релізу `<link rel="modulepreload" href="…">` **для кожного
модуля статичного графа** (і для `pixi-scene.js`, якщо сцена WebGL — production за замовчуванням). Браузер запитує всі
модулі паралельно одразу після HTML; глибина 11 → 1–2. Код лишається нативним ESM без збірки (DEVELOPMENT_RULES:
до 1.0.0 — zero-build), у репозиторії нічого не змінюється, лише сторінки релізу.
- Порядок: спершу точка входу й найглибші модулі критичного шляху; DEV-модулі — лише в `dev.html`.
- Відхилено власником (Q1-б): окремий продакшн-бандл лише для Pages (esbuild уже в devDependencies для вендора) — найменше
  запитів, але друга форма коду (sourcemaps, розбіжність із локальним запуском). Рекомендація: спершу R1, міряти;
  бандл — лише якщо R1 не дає цілей.
- Перевірка: `pages-release` — сторінка релізу має `modulepreload` для кожного модуля замикання й жодного зайвого.

### R2. Стилі

32 таблиці лишаються окремими файлами (власність стилів, docs/styles.md), але сторінка релізу отримує для них
`<link rel="preload" as="style">` у тому самому порядку (Q1 — а, без склеювання). Без змін каскаду.

### R3. Екран завантаження з першої відмальовки (spec 083 крок 3)

**Рішення власника (Q7, 2026-10-30): мінімалістичний екран без зображень.** Заміняє постер spec 083 (рішення 4–5) для
цього етапу; `loader-poster.webp` не вантажиться.

- **Вигляд:** чорний фон на весь екран; по центру — мінімалістичний значок завантаження, **вбудований SVG з
  CSS-анімацією** (без JS, без файлів, без растрових картинок; `prefers-reduced-motion` — статичний значок); під ним
  **рядок мегабайтів** «12.4 / 18.0 МБ» і **смуга прогресу**. Обидві портретна й альбомна орієнтації, логічні пікселі.
- **Розмітка й стилі — inline у `index.html` / `dev.html`** (критичний CSS у `<style>`, ~2–3 КБ разом із SVG), щоб
  екран зʼявився з першого байта HTML, ще до будь-якого модуля й таблиці стилів (T-paint). Без глобалів і класичних
  скриптів (R10).
- **Чесні байти (FR-019, без вигаданих чисел):** release-скрипт записує в сторінку релізу маніфест старту — перелік
  блокуючих ресурсів (модулі замикання, стилі, Pixi-бандл, мінімальний набір R4) зі **стиснутим розміром** (gzip з git для JS/CSS/JSON, медіа як є — див. «Байти рахуються стиснутими»);
  знаменник — їх сума. Чисельник — сума стиснутих розмірів завершених ресурсів з того самого маніфесту (`AssetLoadResult`
  черги + модулі/стилі за `PerformanceResourceTiming`, з кешу теж рахуються як завантажені). Локальний запуск без маніфесту — лише смуга за
  кількістю ресурсів, без МБ.
- `StartupLoaderView` (presentation) підписується на `StartupLoadProgress`, оновлює текст і `transform: scaleX` смуги
  (без перекомпонування), після мінімального барʼєра плавно ховає шар і прибирає його з DOM. Помилка обовʼязкового
  ресурсу — текст помилки й кнопка «Спробувати ще» (spec 047), без нескінченної анімації.
- Атрибут `data-game-ready` на корені після барʼєра — сигнал для вимірювача (R9). Spine-анімація екрана — пізніше,
  опційна (FR-028).

### R4. Мінімальний стартовий набір і черга (spec 083 крок 2, spec 047 FR-003/005/007)

`GameAssetPreloadFacade` замінює `AssetPreloadCoordinator` поверх `AssetLoadQueue` (те саме API й `AssetLoadResult`,
game-cycle незмінний). Каталог ресурсів генерується з поточних `assets/` (спершу лише `legacy` — поведінка та сама).
- **Блокуючі (`blocking`) до T-play:** карта глибин локації (дані гри, точна, FR-023); **поточна фаза доби** (база +
  накладка в сутінки/світанок, 083 рішення 3) у `l`, інакше `legacy`; арти сцени, без яких перший кадр неможливий
  (поплавок, Spine-вудка — або її статичний fallback), Pixi-бандл.
- **Після барʼєра (`prefetch`, по одному, пауза при прихованій вкладці/offline/save-data — FR-017):** інші фази доби
  (наступна раніше за наступну-після), стадії садка, арти інвентаря, будинок/лобі.
- **На вимогу (`interactive`):** відкриття інвентаря/садка — їхні картинки; кораблик — Spine-бандл кораблика (вже лінивий).

### R5. Садок (M3)

Передзавантажувати лише **поточну** стадію заповнення (з моделі садка), решту — `prefetch` після барʼєра або при
відкритті садка.

**Рішення власника (Q3 для садка, 2026-10-30): садок зменшити** через `utils/convert-images.js` якістю **middle**
(WebP 80). Поточні 6 стадій — 2048 px, 0.48–0.89 МБ кожна (разом 3.9 МБ).
- Masters 2048 px — до `asset-sources/items/keepnet/` (ніколи не в релізі; правило конвертації власника).
- Нові `assets/items/keepnet/keepnet--{0..100}.webp` — ~768 px по довгій стороні (×2 від найбільшого розміру показу
  садка; точне число — заміром розміру показу в портреті й альбомі перед конвертацією), ті самі імена, тож посилання не
  змінюються. Режим `--thumbnails` вже робить resize + WebP 80; додати йому `--quality low|middle|high` (як у `--batch`),
  щоб якість задавалась так само, а не числом у коді.
- Очікувано ~60–120 КБ на стадію; одна поточна стадія до T-play замість 3.9 МБ.
- Перевірка: розміри файлів садка ≤ бюджету, кожен шлях — у `git ls-files` (правило релізу).

### R6. Інвентар (M4)

**Рішення власника (Q3 для предметів, 2026-10-30): окремих мініатюр немає — одна картинка на предмет**, завантажена
й декодована один раз і показана в усіх місцях (картка рюкзака, клітинка спорядження, панель інструментів, прев'ю
редактора). Редактор показує предмет крупним планом, тож **найдовша сторона ≥ 1024 px, WebP middle (80)**.

Заміряно (2026-10-30): 29 tracked картинок `assets/items/` = 6.57 МБ (садок 3.9 МБ — R5, решта 2.6 МБ); 12 предметів
(без садка) мають найдовшу сторону > 1024: валізи 2048×2048 (2 × ~0.25 МБ), кораблик 2058×1431 (2 × ~0.25 МБ),
підсака 636×2606, поплавок 219×2525, вудка 1239×2445 (`bamboo-rod-ecip-v1` і `bamboo-rod-unecip-v1` **побайтно однакові** — «з ліскою» і «без» зараз один малюнок; **рішення
  власника 2026-10-30: поки один файл** — `skin.equipment.withLine`/`withoutLine` і `thumbnail.src` на `bamboo-rod-ecip-v1.webp`,
  дублікат `bamboo-rod-unecip-v1.webp` прибрати (перевірити всіх споживачів); окремий арт без ліски — пізніше окремою задачею),
приманки `bread--50`/`oil-worms--100`, батарея `battery-volt--4`.

- **Одне джерело:** кожен арт — один URL; усі місця беруть його з того самого поля конфігурації (як вудка: `skin.thumbnail.src`
  = `skin.equipment.withLine`). Однаковий URL → один запит і одне декодування на сторінку; повторні `<img>` малюються
  з памʼяті браузера миттєво. Перевірка: жоден арт не має двох різних файлів з однаковим вмістом (SHA-256 у `assets/items/`)
  і двох URL на один предмет без причини (кадрування — через `thumbnail.visibleHeight/focusX`, не окремим файлом).
- **Розмір:** найдовша сторона 1024 px (без збільшення менших); для високих вузьких артів (вудка, підсака, поплавок)
  спершу заміряти висоту прев'ю редактора в портреті й альбомі × DPR (≤ 2) — якщо більше 1024, взяти заміряне (≤ 2048),
  записати в цю спеку. Конвертація — `utils/convert-images.js` (resize-режим з `--quality middle`, R5), masters 2048 —
  в `asset-sources/items/`, імена файлів ті самі.
- **Арти, що також у сцені** (підсака `landingNetArt` у вивуджуванні, фон кораблика в `chum_controller`): розмір звіряти
  ще й з розміром показу в сцені (docs/rendering.md — арт близько 1:1); якщо сцені потрібен більший — лишити більший.
- **Коли вантажити:** не до T-play. Після мінімального барʼєра — `prefetch` артів спорядження, що зараз на гравцеві, і
  відкритої за замовчуванням секції; решта — при відкритті інвентаря (`interactive`) через `ImageAssetProvider`
  (`img.decode()` до показу, щоб відкриття не блимало). Ті самі `Image` кешуються провайдером — повторне відкриття без
  мережі й декодування.
- Картинки в DOM — `decoding="async"`; `loading="lazy"` лише для довгих списків поза екраном (сторінки пейджера рюкзака).
- `InventoryUiBootstrap.preloadSlotIcons` (SVG, малі) — лишається.
- Перевірка: `inventory-ui` — один URL на арт, розміри файлів ≤ бюджету (напр. 160 КБ на предмет), кожен шлях tracked.

### R7. Кеш між релізами (M7, Q2) — відкладено

**Рішення власника (Q2, 2026-10-30): не в цій спеці.** Кеш не допомагає гравцю, що заходить уперше, — а саме його
старт є метою. Кеш (спільне сховище або Service Worker) — другий етап, окремою спекою пізніше. Нижче — опис на майбутнє.

Незмінні ресурси (картинки, аудіо, вендор) публікуються один раз у спільне сховище з хешем вмісту в імені
(`<site>/content/<hash>.<ext>`), а сторінки релізу посилаються на них; модулі гри — у теці релізу (як зараз). Повторні
релізи вантажать лише змінене. Потрібні: перелік у release-скрипті, зберігання в gh-pages з утриманням (видаляти
хеші, на які не посилається жоден збережений реліз — правило `--keep`), перевірка `pages-release`. Альтернатива:
Service Worker з кешем (пізніше, офлайн — окреме рішення).

### R8. Аудіо радіо (M6, Q6)

Старт не зачіпає. **Рішення власника (Q6, 2026-10-30): перекодувати лише станцію VOLIA 77.2** — власник і так
навмисно погіршує її звук, висока якість не потрібна; звичайне радіо (свій канал, світове) і звуки ефектів поки не
чіпаємо.

| Файл | Зараз |
| --- | --- |
| `volia/Chomu_z_Kupola_tikayut_na_Irzhavyi_Shelf.m4a` | 41.4 МБ |
| `volia/RADIO_VOLIA.mp3` | 20.3 МБ |
| `volia/RADIO_VOLYA_SHELF.mp3` | 10.4 МБ |

- Ціль: моно, 22.05–32 кГц, ~48 кбіт/с (мовлення «військово-польового» радіо з ефектом рації) → ~0.36 МБ/хв, разом
  орієнтовно у 4–6 разів менше. Остаточний бітрейт — прослуховування власником (дві-три проби: 32/48/64 кбіт/с).
- Формат — один для всіх трьох (MP3 або AAC `.m4a`; обидва грають у мобільних браузерах), посилання в
  `radio_channels.js` оновлює `utils/scan-radio-tracks.js`.
- Інструмент: ffmpeg у системі зараз немає. Додати `utils/convert-audio.js` (аналог convert-images: `--input`,
  `--bitrate`, `--mono`, masters до `asset-sources/audio/radio/volia/`, звіт розмірів) на `ffmpeg-static` як
  devDependency (рішення власника Q6-б, 2026-10-30 — так); бінарник лише для інструменту, не в релізі.
- Програвання станцій лишається потоковим (`<audio>`, без повного декодування). `vinyl-5.mp3` (9.6 МБ, ефект) — не
  чіпаємо за рішенням власника; зафіксовано як ризик памʼяті, коли доріжку `vinyl-5` платівки увімкнено з гучністю > 0.
- Перевірка: розмір кожного файлу VOLIA ≤ бюджету (напр. 12 МБ), шляхи tracked, `radio_channels.js` посилається лише на
  наявні файли.

### R9. Вимірювання і бюджет (A, M9)

- `performance.mark` у бутстрапі (entry → конфіг → композиція → інвентар → сцена готова → перший кадр → барʼєр).
- **DEV-оверлей «ЗАВАНТАЖЕННЯ» (рішення власника Q5, 2026-10-30 — так).** Окремо від «ПРОДУКТИВНІСТЬ» (spec 101), той
  самий механізм перемикача в DevTools, лише `dev.html`, production його не вантажить. Показує після старту:
  - етапи старту з часом від початку (мітки вище) і T-paint / T-play;
  - запити: кількість, байти (передані / з кешу) по типах — модулі, стилі, картинки, аудіо, вендор
    (`PerformanceObserver` / `PerformanceResourceTiming`);
  - топ-10 найбільших і топ-10 найдовших ресурсів;
  - глибину ланцюжка модулів (найдовший ланцюг до точки входу);
  - стан черги прелоадера: що блокує, що в `prefetch`, помилки;
  - кнопку «Копіювати звіт» (текст/JSON у буфер) — щоб власник надсилав цифри з телефона.
  Модуль у `src/dev/` (DEV-only, guard), дані — через порт міток у platform; без впливу на game-cycle.
- Інструмент `npm run measure:startup` (Q5-б — так: Playwright як devDependency) — **не те саме, що оверлей**:
  командний рядок на ПК сам відкриває локальну копію релізу в headless Chromium з емуляцією мережі (4G/3G), холодний (головний, без кешу) і
  теплий старт по 5 разів, пише медіани T-paint/T-play/Bytes/Req у `utils/generated/` і порівнює з бюджетом. Потрібен,
  щоб бачити регрес до релізу без телефона; оверлей — для реального телефона.
- Детермінований бюджет без браузера: перевірка, що стартовий маніфест (блокуючі ресурси) ≤ Bytes-play, а сторінки
  релізу мають повний `modulepreload`.

### R10. Чого не робимо

Не змінюємо геймплей, формули, збереження, game-cycle; не додаємо глобалів і класичних скриптів (екран завантаження —
розмітка й CSS); не вантажимо DEV у production; Spine екрана — не умова старту.
