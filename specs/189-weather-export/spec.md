# Spec 189 — Експорт погоди: усе, що редагує «ПОГОДА», і файли, що переживають зміни коду

Власник, 2026-11-26 (після того, як файл експорту не приніс правок блискавки): «Продумай нормальний експорт щоб я міг
змінювати параметри погоди і експортувати і імпортувати в проект без проблем, погода буде ще змінюватись тому додай
помітку щоб ураховувати це при написанні в логіці експорту.»

## Що є зараз (v0.52.85)

- Файл v2 (`src/dev/weather/weather_export_format.js`, spec 175 / 180 D): `general` — чотири частини (дощ, попіл,
  шторм, вітер, кожна — свій модуль у `raw/weather/`) і / або `locationWeather` локації; на кожну частину — хеш коду
  на момент експорту.
- `npm run apply:weather` (`utils/apply-weather.js`) замінює частину цілком; хеш частини в коді не збігся — конфлікт усієї
  частини (`--force` або переекспорт).
- **Проблеми:**
  1. «ПОГОДА» редагує більше, ніж іде у файл: вигляд блискавки, зорепаду, вода (хвилі, стан моря, покачування), екран
     викиду, шипіння радіації, лічильник Гейгера, течія локації. Правки цих розділів при експорті губляться мовчки
     (так загубились правки блискавки власника).
  2. Будь-яка зміна частини в коді після експорту (новий ключ, інше значення поруч) робить файл конфліктом цілком.
  3. Файл без частини, доданої пізніше, або без ключа, доданого пізніше, відхиляється («missing part», «missing key»).
     Погода ще змінюватиметься — старі файли ставали б непридатними.

## Рішення

- **D1 (агент).** У файл іде **все, що «ПОГОДА» редагує** (крім DEV-перемикачів — `debug.*`, «Автоматична погода»,
  утримання в «Керування»). Кожна частина — свій модуль даних, який `apply:weather` переписує:
  - загальні: `rain`, `ash`, `storm`, `wind` (як були) і нові `lightning`, `starfall`, `water`, `emissionScreen`,
    `radiationGrain`, `geiger` — з `game_config.js` у `raw/weather/<part>_settings.js`, CONFIG ті самі значення;
  - локації: `weather` (`raw/locations/weather/<id>.js`, як був) і новий `current` — течія локації
    (`MAP_DB.<id>.environment.current`) з `location_database.js` у `raw/locations/current/<id>.js`, підключається тим
    самим каталогом.
  Один реєстр частин (`WEATHER_EXPORT_PARTS`) — для експорту, імпорту, статусу «Збереження», скидання й `apply:weather`.
- **D2 (агент).** Формат **v3 — зміни по параметрах**: файл несе `changes` — список `{ part, path, from, to }` (значення
  коду на момент експорту і нове) — і повні значення частин (для імпорту в DevTools і щоб файл можна було прочитати).
  `apply:weather` застосовує **лише зміни**, по одній:
  - у коді `from` → пише `to`; у коді вже `to` → нічого;
  - у коді інше значення (його змінили після експорту) → конфлікт **лише цього параметра** (показ «код / було / стало»);
    `--force` пише `to`;
  - параметра в коді немає (прибрали або перейменували) → пропущено з поясненням (перейменування — таблиця
    `KEY_RENAMES` формату, D4);
  - нові параметри коду, яких файл не знає, не чіпаються; частини, яких файл не має, не чіпаються.
  Тож файл, експортований на старішій версії, застосовується на новій без `--force`, поки його параметри не змінювали.
- **D3 (агент).** Імпорт у DevTools (продовжити налаштування) — ті самі зміни поверх коду: кожен параметр, що є в коді,
  стає `to`; пропущені — у статусі. Файли v1 / v2 читаються, як раніше (повні частини), з D18 spec 187.
- **D4 (агент, «помітка» власника).** Правило в DEVELOPMENT_RULES «Експорт погоди» і коментар над реєстром: новий
  параметр погоди — у модулі частини (нова частина — свій модуль і запис у реєстрі); перейменування ключа — запис у
  `KEY_RENAMES`; формат не зв'язує файл з повним вмістом частини. **Перевірка** (devtools-controls): кожен параметр CONFIG,
  який «ПОГОДА» показує для редагування, належить частині реєстру — падає, щойно новий параметр погоди не потрапляє в
  експорт.
- **D5 (агент).** Перенесення даних у модулі — структурна зміна: CONFIG до й після однаковий (перевірка порівнює), звіт
  ігрового циклу без змін. Коментарі біля ключів у `game_config.js` для перенесених частин замінюють назви й описи
  параметрів (`parameter_labels.json`, вже є для кожного ключа) — `apply:weather` переписує модуль цілком, як для дощу.

## Модель

- `WEATHER_EXPORT_PARTS`: `{ id: { level: "general" | "location", module(id?), exportName, configPath(id?), label,
  header } }`.
- Файл v3: `{ format, formatVersion: 3, gameVersion, exportedAt, general?: { part: value }, locationId?,
  location?: { part: value }, changes: [{ part, path, from, to }] }` (`part` — `general.<id>` або `location.<id>`,
  `path` — крапками всередині частини).
- `applyLeafChanges(current, changes)` → `{ next, applied, already, conflicts, missing }` — одна функція для
  `apply:weather` і DevTools.

## Перевірки

- apply-weather: v3 — застосовується лише змінене; новий ключ у коді після експорту не заважає; змінений у коді параметр
  — конфлікт лише його, `--force` пише; прибраний — пропущено; старі v2 / v1 читаються; кожна частина реєстру пишеться
  у свій модуль і читається грою.
- weather: експорт DevTools несе зміни всіх частин, включно з блискавкою й водою; імпорт ставить їх у гру.
- devtools-controls: кожен параметр «ПОГОДА» — у частині реєстру (D4).
- config-runtime / game-cycle: CONFIG після перенесення той самий.
