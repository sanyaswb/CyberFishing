## Рішення (пропозиція; позначене Q — питання власнику)

### D1. Модель погоди: стани, інтенсивність, наростання й згасання (етап A)

Погода — два незалежні процеси з інтенсивністю 0…1 кожен:

- **Опади:** `clear` → `rain` → `storm` (гроза лише після дощу, назад через дощ). Кожен стан триває випадковий час із
  діапазону локації й має цільову інтенсивність із діапазону; поточна інтенсивність плавно йде до цільової
  (наростання `fadeIn`, згасання `fadeOut`, крива smoothstep), тому дощ не «клацає». `storm` — окрема інтенсивність
  0…1 поверх дощу (темрява неба, частота блискавок, вітер).
- **Туман:** `none` ↔ `fog`, свій шанс, тривалість, інтенсивність, фази доби, у які він можливий (типово ранок і ніч),
  і свої часи наростання/згасання.
- **Блискавки:** поки `storm > 0`, модель планує удари з інтервалом, що коротшає з інтенсивністю; кожен удар — подія
  (лічильник `strikeSerial`, варіант, відстань 0…1). Відстань дає затримку грому й силу спалаху. Візуал і звук лише
  читають подію.

Знімок погоди (той самий об'єкт, перезаписується на місці): `weather.rain`, `weather.storm`, `weather.fog`,
`weather.cloud` (похідна: скільки неба затягнуто), `weather.strikeSerial/strikeVariant/strikeDistance`, а також
**сумісні поля** для наявних споживачів, щоб баланс кльову й радіо не змінився без рішення власника:
`isRaining = rain ≥ rainThreshold`, `isFoggy = fog ≥ fogThreshold`, `wind.rainMult` = лінійно з `rain` у
`rainMultiplier` (при `rain` = 0 — 1).

Конфігурація локації (`MAP_DB.<id>.weather`, нова форма; стару `chances/updateIntervalMs` прибрати разом зі змінами
споживачів):

```js
// Стартові значення (власник, 2026-11-09: «підбери сам, дощ від 1 хв реального часу до 10, далі — балансування»).
weather: {
  precipitation: {
    clear: { weight: 0.70, durationSec: [180, 900] },
    rain:  { weight: 0.25, durationSec: [60, 600], intensity: [0.3, 0.8] },
    storm: { weight: 0.3,  durationSec: [60, 240], intensity: [0.6, 1.0] }, // лише після rain, потім знову rain
    fadeInSec: 20, fadeOutSec: 30,
  },
  fog: { chance: 0.15, phases: ["morning", "night"], idleSec: [120, 600], durationSec: [120, 600], intensity: [0.4, 1.0],
    fadeInSec: 30, fadeOutSec: 45 },
  lightning: { intervalSec: [25, 6], distance: [0.2, 1.0] }, // інтервал при storm 0 → 1
  thresholds: { rain: 0.15, fog: 0.3 },
},
```

Усі тривалості й переходи — у **реальних секундах** (власник, Q2): дощ триває 1–10 хвилин реального часу за будь-якого
прискорення ігрового годинника. Вибір наступного стану — за вагами `weight` (гроза — лише з дощу). Значення —
стартові, власник балансує їх у DevTools «ПОГОДА». Нічого не алокується в кадрі; модель — чистий клас
домену `game/domain/weather/` (без DOM), RNG і конфігурація інжектуються з bootstrap.

**RNG і game-cycle (Q1).** Зараз погода бере числа зі спільного RNG гри; будь-яка зміна моделі змінює послідовність для
риби, тож digest game-cycle зміниться. Пропозиція: погоді — власний потік RNG із сіда сесії (більше ніколи не
впливатиме на рибу) і один схвалений власником re-baseline у коміті етапу A з поясненням.

**DEV.** Розділ DevTools «ПОГОДА»: поточний стан, інтенсивності, таймер стану; примусити стан (ясно / дощ / гроза /
туман) з інтенсивністю й часом переходу, «удар блискавки зараз», заморозити погоду; живі правки `MAP_DB.<id>.weather`.

### D2. Відблиски на воді (етап B, першочергово)

Відблиски — маленькі яскраві іскри з адитивним змішуванням, **прив'язані до тих самих хвиль**, що вже рухають воду:

- На кожному кроці води (30/с) `WaterWaveField` уже рахує нахил хвилі в кожній клітинці карти; той самий прохід
  записує «яскравість відблиску» в незайнятий синій канал (без додаткового циклу). Клітинки, де яскравість вища за
  поріг, стають іскрами: позиція — центр клітинки з детермінованим зсувом, розмір і яскравість — з яскравості та
  перспективи (`surfaceScaleAt`: дальні іскри дрібніші й густіші). Хвилі рухаються — іскри самі мерехтять.
- **День (`day`):** сонячні іскри по всій воді (у зелених зонах).
- **Схід і захід (`morning`, `evening`) — доріжка від сонця** (власник, Q5): така сама, як від місяця, теплого кольору.
- **Ніч (`night`) — доріжка від місяця.**
- **Доріжка** (сонце й місяць — один механізм, свої налаштування): іскри лише в смузі під світилом; вісь смуги — X
  світила, ширина задається **на дальньому й ближньому краях води** (у перспективі смуга розширюється до глядача),
  м'якість країв; під іскрами — м'яка світла доріжка (один градієнтний спрайт). Позиція світила — **Q3**.
- Зміна фаз — плавна: сила кожного режиму йде за тими самими прозоростями фаз, що й фони (`timeOfDayLayers`).
- Погода гасить відблиски: `× (1 − cloud)`; у дощ/грозу/туман їх майже немає.
- Малюються одним `ParticleContainer` (один draw call, без нового фільтра й без власного шейдера — без ризику CSP,
  TK-256); текстура іскри генерується один раз при старті сцени (без нового асету). Пул іскор фіксований
  (`maxSparkles`), нічого не створюється в кадрі; кадр сцени — лише на кроці води (як зараз).

Конфігурація з живими правками в DevTools (вода → «Відблиски»):

```js
CONFIG.canvas.water.glints = {
  enabled: true,
  maxSparkles: 600,
  day: {
    intensity: 1.0,
    threshold: 0.72,
    size: 3,
    sizeFar: 1,
    density: 1.0,
    color: "#ffffff",
  }, // уся вода
  // Доріжки: ширини — частки ширини води на дальньому / ближньому краї.
  sunPath: {
    intensity: 1.0,
    threshold: 0.6,
    size: 3,
    sizeFar: 1,
    widthFar: 0.05,
    widthNear: 0.3,
    softness: 0.5,
    pathGlow: 0.3,
    color: { morning: "#ffe2b0", evening: "#ffb46a" },
  },
  moonPath: {
    intensity: 0.8,
    threshold: 0.6,
    size: 2.5,
    sizeFar: 1,
    widthFar: 0.04,
    widthNear: 0.25,
    softness: 0.5,

```

Вбудовування: новий `PixiWaterGlintRenderer` у `src/platform/browser/scene/` (Pixi-типи не виходять за межі сцени),
одразу над водою у `PixiSceneLayer`; модель кадру (фаза, сила сонця/місяця, X місяця, хмарність) будує presentation;
у бандл сцени додаються `ParticleContainer`, `Particle` (`utils/vendor-libraries.js`, маніфест).

### D3. Spine-шари локації (етап C)

Власник ділить карту на шари; гра розставляє їх по глибині. Головне правило: **один скелет = один рівень глибини**
(скелет не можна «розрізати» поплавком чи вудкою). Порядок сцени знизу вгору:

| #   | Шар           | Хто малює                       | Що в ньому                                                  |
| --- | ------------- | ------------------------------- | ----------------------------------------------------------- |
| 1   | `sky`         | Spine власника                  | небо, хмари, сонце, місяць, зірки, блискавки (за будинками) |
| 2   | фон фази доби | зображення (як зараз)           | суша, будівлі, вода; **небо прозоре**                       |
| 3   | вода          | гра                             | хвилі (копія фону), відблиски, кола від крапель і човна     |
| 4   | `far-fog`     | Spine власника (необов'язковий) | туман над водою, за предметами гравця                       |
| 5   | `near`        | Spine власника (необов'язковий) | анімовані предмети перед водою: очерет, пірс, дерева        |
| 6   | світ          | гра                             | човен, поплавок, волосінь, вудка, риба, бризки крапель      |
| 7   | `near-fog`    | Spine власника (необов'язковий) | туман перед гравцем, тонкий                                 |
| 8   | дощ, спалах   | гра                             | краплі дощу, спалах блискавки на всю сцену                  |
| 9   | HUD           | 2D canvas                       | як зараз                                                    |

Статичне (будівлі, берег) лишається в зображенні фону — Spine лише для того, що рухається (rendering 18, 21). Вода
лишається зображенням фону, бо хвилі зсувають саме його. Час доби в Spine — анімації фаз, які гра змішує так само, як
фони (`timeOfDayLayers`). Інтенсивність погоди — альфа доріжок анімацій. Контракт імен, координат, атласів і подій —
у [spine-requirements.md](spine-requirements.md); перевірка `location-spine` відхиляє експорт, що його порушує.

Завантаження: перший кадр не чекає Spine (R11): поки скелет неба не готовий, малюється його статична картинка
`<шар>--scene.webp` (як у вудки й човна); решта шарів — у шарі 2 плану завантаження. Нова локація записує в цю спеку
обсяг текстур (rendering 19).

### D4. Дощ (етап D)

- **Краплі:** спершу обирається точка приземлення на землі/воді, потім крапля падає до неї зверху під кутом вітру —
  так кожна крапля «знає» свою глибину: дальні менші й повільніші (перспектива води), ближні більші. Один
  `ParticleContainer`, текстура-штрих генерується при старті, пул за `maxDrops`; кількість = інтенсивність дощу ×
  густина. Дальній дощ — 1–2 шари `TilingSprite` (майже нуль CPU) для об'єму.
- **Падіння на воду:** точка приземлення в зеленій зоні закидання (`world.clipRegions`) → кільце хвилі через
  наявний `WaterWaveField.addRipples` (те саме, що кола від човна) + маленький сплеск-спрайт. Без нових масок.
- **Падіння на тверде (пробно, Q6):** новий тип зон «поверхні для бризок» у редакторі зон (spec 129): прямокутники/маска
  як у зон закидання. Бризки — 2–4 частинки на краплю. Якщо на телефоні вони замалі — вимикаємо тип зон без переробок
  (прапорець у конфігурації).
- Без фільтрів на весь екран. Звук дощу — у плані завантаження, вантажиться лише коли почався дощ (DEVELOPMENT_RULES:
  аудіо — при першому використанні).

### D5. Гроза (етап E)

- Небо темніє: анімація `storm` у скелеті неба (альфа доріжки = інтенсивність грози) + один напівпрозорий темний
  спрайт на всю сцену (одна заливка, без фільтра), сила за `storm`.
- Удар блискавки: гра програє `lightning-N` у скелеті неба; подія Spine `flash` дає момент і силу спалаху → гра
  піднімає яскравість сцени (адитивний білий спрайт, кілька кадрів) і рахує затримку грому від відстані удару.
- Звук грому й тріск радіо від грози (задача з `tasks.md`) — у цьому етапі, якщо власник дасть звуки (**Q7**).

### D6. Туман (етап F)

Туман — Spine-скелети власника (`far-fog`, `near-fog`), гра керує: альфа всього скелета = інтенсивність туману,
швидкість анімації — від вітру, колір — анімації фаз доби. Ручне керування — DevTools «ПОГОДА». Відблиски гаснуть за
туманом (D2). Вплив туману на видимість поплавка — **Q4** (поки ні).

### D7. Живі хвилі: вітер, ніч, гроза, розсинхрон (TK-289, v0.50.98)

Запит власника (2026-11-13): «потрібно виправити однотонність хвиль, вони повинні залежати від вітру та мати невеликий
розсинхрон, вони занадто однакові та неприродні, також в ночі хвилі повинні зменшуватися так як вночі частіше штиль,
при штормі хвилі збільшуються».

Було: `WaterWaveField` — п'ять синусоїд зі сталими висотою, швидкістю й напрямом (`CONFIG.canvas.water`); усі гребені
рухалися з однією швидкістю, тож візерунок повторювався «в ногу»; погода й час доби на хвилі не впливали.

- **Стан моря** — `SeaStateResolver` (presentation, `src/game/presentation/world/`): з вітру (`EnvironmentSystem`, напрям
  −1/0/1; гроза рахується як повний вітер), ночі (`backgroundTimeBlend`, як нічний фон) і грози (модель погоди) — множники
  висоти, швидкості й довжини хвиль і напрям руху (за вітром; у штиль — останній). Кожне значення йде до цілі зі сталою
  часу `smoothingSec` (реальний час): море наростає й стихає, а не стрибає. Оновлюється раз на кадр у моделі світу
  (`world.sea`); той самий стан читає `FloatWaveRocking` (висота × `amplitudeScale`, темп × швидкість / довжину), тож
  поплавок гойдається з тією самою водою. `CONFIG.canvas.water.seaState` (живі правки, підписи, перевірка схеми).
- **Розсинхрон** — у `WaterWaveField.write`: пройдена гребенями відстань `travelPx` інтегрується рендерером води з
  швидкості й напряму стану моря (зміна вітру не дає стрибка візерунка); `variation` (`CONFIG.canvas.water.variation`):
  довші складові швидші (`dispersion`, як на глибокій воді), кожна складова повільно «дихає» висотою у своєму ритмі
  (`breath`, `breathSec`), дві довгі повільні «групові» хвилі роблять плями вищих і нижчих хвиль (`groupDepth`,
  `groupScale`, `groupSpeed`). Без `travelPx`/`variation` поле побайтово те саме, що раніше (доведено порівнянням із
  попередньою версією, 10 випадків).
- Ціна: крок води 0,159 → 0,186 мс на ПК (30 кроків/с), GPU без змін (той самий фільтр).
- Перевірки: `weather` — стан моря (штиль/вітер/ніч/сутінки/гроза, плавне наростання, поворот без стрибка, вимкнено = як
  задано); `float-pose` — поплавок іде за станом моря (висота ×2 / ×0,5 точно, темп); `scene-layer` — розсинхрон (шлях
  задає візерунок, нульова варіація = звичайне поле, дисперсія, дихання, групи), висота моря подвоює зсув фільтра.

### TK-290 — окремий перемикач хвиль (v0.50.100)

Власник (2026-11-13): вимикати хвилі окремо, а брижі від дощу (викривлення шейдера, не кільця) лишати. Було: хвилі й брижі —
одна карта зсуву під одним `DisplacementFilter`; «Брижі на воді» вимикали все, сила брижів була часткою висоти хвиль із
станом моря (уночі й у штиль брижі слабшали, «Сила хвилі» 0 гасила і їх). Зміна: `CONFIG.canvas.water.waves` — лише хвилі
(вимкнено: `WaterWaveField.write` з `amplitude` 0 пише спокійну карту, брижі додаються після; поплавок не гойдається);
діапазон фільтра — базова «Сила хвилі» × множник моря лише вище 1, хвилі займають свою частку, брижі (`addRipples` зі
`scale` = 1 / діапазон) завжди в одиницях базової «Сила хвилі». Із `amplitude` 1 поле те саме, що раніше. Перевірки
`scene-layer` (`checkWavesSwitch`: хвилі вимкнено — карта спокійна, крім брижів; брижі однакові вночі й у грозу; ніч не
звужує діапазон) і `float-pose` (без хвиль поплавок нерухомий); обидві падають на старому коді.

### TK-291 — погода в розділі сцени, підсекції стану моря, оверлей «Погода й хвилі» (v0.50.101)

- DevTools «ПОГОДА» малюється всередині «🖼️ СЦЕНА WebGL» (`SceneLayerDevSection` викликає `renderWeather`; без
  розділу сцени — у панелі, як раніше); підсекція води називається «🌊 Вода: хвилі й брижі (CONFIG.canvas.water)».
- `CONFIG.canvas.water.seaState`: спільні `enabled`, `smoothingSec`; `normal` — звичайний стан (`calmAmplitude`,
  `windAmplitude`, `windSpeed`, `nightAmplitude`); `storm` — подія «гроза» (`amplitude`, `speed`, `wavelength`). Значення
  ті самі, змінилася лише форма (`SeaStateResolver`, підписи, перевірка схеми).
- Оверлей «ПОГОДА й хвилі» (`WeatherOverlayModule`, група «Сцена й погода»): опади, сила грози / дощу / туману 0…1,
  вітер (напрям, сила 0…1, вручну), ніч, фактичні амплітуда, довжина й швидкість хвиль (база × поточні множники стану
  моря) і їхній напрям, блискавки. Читає `GameCompositionRoot.getWeatherReading()` → `WeatherStatusReader`
  (presentation, один об'єкт). Перевірки: `weather` (значення = база × множники в грозу з вітром, без хвиль — 0, оверлей
  показує їх), `config-runtime` (модуль складено, до гри — «Гра ще не створена»).
